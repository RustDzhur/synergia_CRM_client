# Мобильные и планшетные приложения: архитектура и обязательные правила

Файл написан для того, кто будет делать приложения (Claude), и для владельца. Здесь — **что строим, из чего и по каким правилам**.
Порядок работ, статусы и журнал — в `docs/MOBILE_ROADMAP.md`.

**Протокол.** Перед любой работой над мобильной частью прочитать оба файла целиком. Идти по ROADMAP сверху вниз, не перескакивать через этапы.
После каждого шага отметить статус и записать, что проверено, а что нет. Правила из раздела 5 не нарушать, даже если так быстрее.

Что проверено, а что нет, указано по месту. Всё, помеченное «проверить при реализации», — гипотеза из документации, а не факт.

## 1. Цель и главный принцип

Приложения в App Store и Google Play для iPhone, iPad, телефонов и планшетов Android, которые **не живут своей жизнью**: любое изменение сайта
(`https://www.firmspace.de`) — интерфейс, логика, новые разделы, данные — сразу видно в приложениях, без правки и повторной отправки приложений в магазины.

Отсюда один принцип: **сайт — единственный источник интерфейса и логики; приложение — тонкая нативная оболочка вокруг него** плюс то,
что браузер сам не умеет (push, биометрия, файлы, ссылки, вход без пароля). Всё остальное — производные правила ниже.

«Сразу» означает: деплой на Vercel → при следующей загрузке страницы (открытие приложения, возврат в него, переход) пользователь уже на новой версии.
Магазины участвуют только тогда, когда меняется сама оболочка (раздел 15).

## 2. «Разные экраны» — это не разные приложения

Собираем **два** бинарника, а не шесть:

| Сборка | Что покрывает | Карточка в магазине |
|---|---|---|
| iOS, универсальная | iPhone любых размеров и iPad (mini, Air, Pro 11", Pro 13") | App Store: одна карточка, скриншоты для iPhone и для iPad |
| Android, AAB | телефоны, складные, планшеты | Google Play: одна карточка, скриншоты для телефона, 7" и 10" планшета |

Под разные экраны подстраивается **одна адаптивная вёрстка сайта** (раздел 11): приложение показывает тот же сайт, а макет выбирается по ширине окна.
Отдельные «планшетные приложения» не делаем: это удвоило бы релизы и проверки в магазинах без пользы для человека. Планшет — это режим макета, а не сборка.

## 3. Архитектура

```
Пользователь (iPhone / iPad / телефон Android / планшет Android)
   │
   ▼
Нативная оболочка (Capacitor 8): iOS — WKWebView, Android — System WebView
   ├─ плагины: push · биометрия · Keychain/Keystore · файлы, камера, шаринг · ссылки в приложение · системный браузер
   └─ в WebView грузится один адрес: https://www.firmspace.de/…   (страница «нет сети» — локальная, внутри оболочки)
   │
   ▼
Сайт (Next.js на Vercel)  ← единственный источник UI и логики   ← ветка → «заливай» → main → деплой
   ├─ /api/…      те же маршруты, что у сайта (больше 180)
   └─ /api/app/…  новые: конфиг оболочки, сессии устройств, push-токены
   │
   ▼
MongoDB · Firebase Storage · Stripe · провайдеры каналов
```

Что где живёт:

| Что | Где | Как меняется |
|---|---|---|
| Экраны, логика, стили, переводы, API | репозиторий сайта (`crm_client`) | деплой на Vercel → сразу во всех приложениях |
| Мост со стороны сайта (`utils/native/*`, `data-app`, `/api/app/*`) | репозиторий сайта | деплой |
| Правила и статус мобильной части | `docs/MOBILE.md`, `docs/MOBILE_ROADMAP.md` | правки в git |
| Нативный проект: Capacitor, `ios/`, `android/`, иконки, разрешения, `capacitor.config.ts` | отдельный репозиторий `firmspace-mobile`, папка `~/Developer/firmspace-mobile` (вне iCloud) | сборка и загрузка в магазины — редко |
| Файлы подписи и ключи (`.p8`, keystore, пароли) | не в git; хранит владелец | — |

Отдельный репозиторий оболочки, а не папка внутри сайта — по трём причинам: (1) сайт живёт в iCloud-папке `~/Documents`, где файлы становятся «dataless» и ломают Gradle, Xcode и npm;
(2) `tsconfig.json` сайта включает все `**/*.ts(x)` и подхватил бы код оболочки; (3) оболочка меняется редко и у неё свои секреты и свой цикл выпуска.

## 4. Почему Capacitor и живой сайт

### 4.1 Рассмотренные варианты

| Вариант | Единый источник | Магазины | Push, биометрия | Вывод |
|---|---|---|---|---|
| PWA («на экран Домой») | да | нет карточки | ограничено, биометрии нет | не решение; манифест и иконки — необязательный бонус |
| **Capacitor + живой сайт (`server.url`)** | **да, мгновенно** | да | да, плагины | **выбран** |
| Capacitor со встроенным статическим сайтом + Live Updates | да, через канал обновлений (минуты) | да | да | запасной путь (4.3) |
| React Native / Expo с WebView | да (тот же WebView) | да | да | ничего не даёт сверх Capacitor |
| Полностью нативные приложения | нет, дублирующий код на 2–3 платформы | да | да | противоречит требованию «один источник» |

### 4.2 Честная оговорка про `server.url`

Документация Capacitor помечает `server.url` и `allowNavigation` как «не для продакшена» — это рекомендация для разработки. На практике так выпущено много приложений,
задокументированных отказов магазинов именно за это мы не нашли (обсуждение Capacitor #5075 и статья Capawesome; проверено 2026-09-30), но **гарантии нет**.
Реальный риск — не техника, а ревью Apple по правилу 4.2 («приложение — просто обёртка сайта»). Поэтому обязательные меры:

1. С первой версии — настоящие нативные функции: push, Face ID / отпечаток, файлы и камера, «Поделиться», ссылки в приложение, бейдж, haptics, экран «нет соединения».
2. `server.errorPath` — локальная страница «нет сети» внутри оболочки, на трёх языках.
3. Принудительное обновление оболочки: `minShellVersion` из `/api/app/config` (6.2).
4. Определение возможностей (`hasPlugin`), а не версий (6.3).
5. Белый список адресов и CSP (раздел 13).
6. Service worker не кеширует страницы и данные CRM (иначе «одного источника» не будет). Единственное допустимое исключение — решение D16 (18.8): неизменяемые ассеты `/_next/static/*` по версии сборки; данные — только в SQLite (18.2).
7. Демо-аккаунт и понятные заметки ревьюеру (12.1, правило 2.1).

### 4.3 Запасной путь, если магазин откажет

Live Updates (Capawesome / Capgo) со **встроенным статическим сайтом**: оболочка содержит копию интерфейса и подтягивает новые версии из канала обновлений.
Требует статического экспорта (`output: 'export'`, `generateStaticParams`), абсолютного адреса API и CORS для ~180 маршрутов — крупный рефакторинг.
Пока не делаем и не проектируем под него; включаем в работу только при реальном отказе, который не снимается объяснением.

## 5. Обязательные правила

**Архитектура**

* **R1. Ничего своего в оболочке.** Ни экранов, ни бизнес-логики, ни копии интерфейса. Исключения: страница «нет сети», экран «обновите приложение», экран работ, системные диалоги разрешений.
* **R2. Сайт в обычном браузере работает как раньше.** Любой нативный вызов — только через `utils/native/*`, за `isNativeApp()` и `hasPlugin(name)`, с веб-запасным вариантом.
* **R3. Никаких ветвлений «приложение / не приложение» при рендере.** Только CSS-вариант `app:` (атрибут `data-app` на `<html>`) или хук `useIsApp()` (false на первом рендере, true после монтирования). Иначе — ошибки гидрации.
* **R4. Одно меню и один набор маршрутов.** Навигация телефона строится из `components/crm/Sidebar/menuItems.ts` с учётом `useVisibleMenu.ts` (права и тариф). Отдельных «мобильных» списков разделов нет.
* **R5. Совместимость назад.** Оболочка живёт у людей месяцами. Сайт не должен ломаться на оболочке предыдущих версий: новые нативные возможности — только за `hasPlugin`; ломающее изменение — только через повышение `minShellVersion`.
* **R6. Новые серверные маршруты для приложения — под `/api/app/*`.** Существующие маршруты ради приложения не меняем (кроме обратно совместимых расширений).

**Процесс**

* **R7. Ветки `feat/mobile-*`, коммиты локально, конкретными путями.** Никогда `git add -A`: iCloud создаёт дубли вида `name 2.ts`. В `main` — только по слову владельца «заливай» / «залей».
  Помнить: каждый деплой в прод мгновенно попадает во все приложения, поэтому правки, затрагивающие мобильный режим, проверяются особенно тщательно.
* **R8. `next build` не запускаем в папке проекта** — только в scratch-копии, как в остальных работах проекта. Типы и Tailwind проверяем там же (`twcheck.sh`).
* **R9. Нативный проект — вне iCloud** (`~/Developer/firmspace-mobile`). Внутри `~/Documents` при включённой «Оптимизации хранилища» файлы уходят в облако и сборка ломается.
* **R10. Тестовые данные.** Только временные пользователи `zz-integr-test*@example.com` с очисткой после проверки. Единственное исключение — демо-аккаунт для ревью магазинов: создаётся осознанно (M5.3) и потом не трогается.
* **R11. «Готово» — только с фактом проверки.** У каждой задачи ROADMAP есть критерий готовности. Что не проверялось на симуляторе или реальном устройстве, записываем как «не проверено», а не «работает».
* **R12. Секреты.** В оболочке и её репозитории нет серверных секретов. Ключи подписи (`.p8`, keystore, пароли) не в git. `GoogleService-Info.plist` и `google-services.json` секретами не считаются, но лежат только в приватном репозитории.
  Ключи, которые владелец присылает в чат, не используем: просим перевыпустить и добавить через `vercel env add`.
* **R13. Минимум плагинов и разрешений.** Каждый плагин и каждое разрешение записываются в ROADMAP с пометкой «зачем». Лишнее не добавляем: магазины проверяют формы приватности.
* **R14. Правила магазинов (раздел 12) блокируют отправку.** Не отправляем сборку в ревью, пока пункты 12 не выполнены.

**Вёрстка** (подробности — раздел 11)

* **R15. Mobile-first, десктоп не ломаем.** База — телефон; `md:` — планшет; `tab:` — планшет в ландшафте; `lg:` — десктоп «как сейчас». После каждой правки макета проверяем 1440 и 1920: там ничего не должно измениться.
* **R16. Никаких `100vh` и `h-screen` в новом коде** — `h-[100dvh]`; отступы у краёв экрана — через `env(safe-area-inset-*)`.
* **R17. Ничего, что работает только по `:hover`.** На сенсорном экране hover нет.
* **R18. Тема Tailwind заменяет шкалы:** отсутствующий ключ молча не создаёт CSS. Нестандартные размеры — через `[...]`, проверка `twcheck.sh`. После новых цветовых классов — `node scripts/gen-dark-css.js`.
* **R19. Все новые тексты — на трёх языках** (`messages/{de,en,ua}.json`); тексты оболочки (разрешения, «нет сети», «обновите») — тоже.
* **R20. Платёжные функции сайта в приложении не показываем** (12.3).

**Офлайн** (этап 7, подробности — раздел 18)

* **R21. Офлайн-слой работает только в приложении** (`isNativeApp()`). Сайт в обычном браузере не меняется.
* **R22. Локальные данные CRM — только в SQLite через `utils/native/db.ts`.** Ни `localStorage`, ни IndexedDB для данных CRM.
* **R23. Очередь неотправленных правок не теряется молча.** Удаляется только по явному действию пользователя (с предупреждением), при выходе с подтверждением или при отзыве устройства.
* **R24. Чужие изменения молча не перезаписываем** (18.6): конфликт по одному полю решает человек.
* **R25. Деньги, фискальные чеки, доставка и отправка внешних сообщений — только онлайн** (18.1).

## 6. Контракт «сайт ↔ оболочка»

### 6.1 Признаки режима приложения

* Оболочка добавляет к User-Agent суффикс `FirmspaceApp/<shellVersion> (ios|android)` (`appendUserAgent` в `capacitor.config.ts`; версию скрипт берёт из `package.json` оболочки; точное имя опции проверить по документации Capacitor 8 в M3.2).
* Короткий скрипт в `<head>` (`app/[locale]/layout.tsx`) до отрисовки выставляет на `<html>` атрибуты `data-app="ios|android"` и `data-shell="<версия>"`; у `<html>` — `suppressHydrationWarning`.
* Tailwind-вариант `app:` (`[data-app] &`). Всё, что отличается в приложении только видом, делается им.
* Мост `window.Capacitor` внедряет оболочка; сайт обращается к нему **только** внутри `utils/native/*`.
* Если UA говорит «приложение», а моста или плагина нет, макет режима приложения включён, а нативные функции — выключены.

### 6.2 `/api/app/config` (GET, публичный, кеш не дольше минуты)

```json
{
  "minShellVersion":    { "ios": "1.0.0", "android": "1.0.0" },
  "latestShellVersion": { "ios": "1.0.0", "android": "1.0.0" },
  "storeUrl":           { "ios": "…", "android": "…" },
  "maintenance":        { "on": false, "message": { "de": "", "en": "", "ua": "" } },
  "build": "<коммит текущего деплоя>",
  "features": { "push": true, "biometric": true }
}
```

Значения лежат в `config/app.ts` (деплой и так мгновенный, отдельная админка не нужна). Оболочка и сайт читают ответ при запуске и при возврате на передний план:

* версия оболочки ниже `minShellVersion[platform]` — экран «Обновите приложение» с кнопкой в магазин;
* `maintenance.on` — экран работ;
* `minShellVersion` поднимаем **только когда новая оболочка уже одобрена в магазине** — иначе люди упрутся в «обновите», а обновления ещё нет.

### 6.3 Фасад `utils/native/`

Единственное место, где сайт знает о нативной части. Файлы (создаются по этапам ROADMAP):

| Файл | Назначение |
|---|---|
| `env.ts` | `isNativeApp()`, `platform()`, `shellVersion()`, `hasPlugin(name)`, `useIsApp()` |
| `auth.ts` | безопасное хранилище токена устройства, биометрия, обновление сессии |
| `push.ts` | разрешение, регистрация токена, бейдж, нажатие на уведомление |
| `files.ts` | `saveAndOpen(blob, name)`, шаринг, выбор фото |
| `browser.ts` | `openExternal(url)`, `openOAuth(url)` |
| `chrome.ts` | статус-бар под тему, клавиатура, haptics |
| `links.ts` | обработка `appUrlOpen` (ссылки в приложение) |
| `db.ts` | локальная зашифрованная SQLite: кеш и очередь правок (этап 7, 18.2) |
| `network.ts` | состояние сети и событие «связь появилась» (этап 7, 18.4) |

Шаблон каждой функции: вне приложения — обычное поведение сайта.

```ts
export async function openExternal(url: string) {
  if (hasPlugin("Browser")) return (await plugin("Browser")).open({ url });
  window.open(url, "_blank", "noopener");
}
```

Как сайт достаёт плагины — **открытый вопрос, решается спайком M3.6**: (а) через внедрённый оболочкой `window.Capacitor.Plugins` без зависимостей в `package.json` сайта (по умолчанию) или
(б) через npm-пакеты `@capacitor/core` и плагины, импортируемые динамически только в приложении. Результат спайка записываем сюда.

Кандидаты в плагины (подтвердить актуальность и совместимость с Capacitor 8 при установке; npm недоступен из песочницы, пакеты ставит терминал владельца):
`@capacitor/app`, `@capacitor/browser`, `@capacitor/status-bar`, `@capacitor/keyboard`, `@capacitor/haptics`, `@capacitor/share`, `@capacitor/filesystem`,
`@capacitor/screen-orientation`, `@capacitor/splash-screen`, `@capacitor/network`, `@capacitor-community/sqlite` (этап 7: SQLCipher; совместимость с Capacitor 8 не подтверждена), `@capacitor-firebase/messaging` (push), плагин безопасного хранилища Keychain/Keystore, плагин биометрии, плагин бейджа, `@capacitor/assets` (иконки и сплэш).

### 6.4 Версии и совместимость

* `shellVersion` — семвер оболочки. Возможности определяем по `hasPlugin`, а не по версии: так старая оболочка без нового плагина не ломается.
* В ROADMAP ведём таблицу «какой релиз оболочки что умеет» — по ней решаем, когда можно поднять `minShellVersion`.

### 6.5 Свежесть сайта в живой сессии

* HTML отдаётся сервером, статика Next имеет хеши в именах. Оболочка ничего не кеширует сверх штатного HTTP-кеша WebView.
* Сессия может жить днями: после деплоя старые чанки исчезают. Поэтому при возврате на передний план (`visibilitychange`) и раз в 30 минут сайт сравнивает `build` из `/api/app/config` со своим (`NEXT_PUBLIC_BUILD` из `VERCEL_GIT_COMMIT_SHA` через `env` в `next.config.js`)
  и при расхождении мягко перезагружается на ближайшей навигации (сразу — если нет несохранённого ввода). Проверить при реализации.

## 7. Вход и сессии

Сегодня: `POST /api/auth/signin` возвращает JWT на 1 день без refresh; токен лежит в `localStorage("token")` и уходит заголовком `Authorization: Bearer`; куки не используются.
Для приложения этого мало: человек должен войти один раз и дальше открывать приложение по Face ID или отпечатку.

Решение — **сессия устройства**, новые маршруты под `/api/app/session` (существующие `/api/auth/*` не меняем):

* `POST /api/app/session` `{ email, password, deviceName, platform, shellVersion }` — проверка такая же, как в `signin`; ответ `{ token, deviceToken, expiresAt }`. `token` — тот же JWT, что даёт сайт.
  `deviceToken` — случайные 256 бит (base64url); в базе лежит только его SHA-256 (модель `DeviceSession`: user, tokenHash, platform, deviceName, shellVersion, createdAt, lastUsedAt, expiresAt, revokedAt).
* `POST /api/app/session/refresh` `{ deviceToken }` — новый JWT и **новый** deviceToken (ротация; предыдущий действует ещё 2 минуты на случай гонки запросов). Срок скользящий, 90 дней.
  Повторное использование уже отозванного токена отзывает все сессии этого устройства.
* `DELETE /api/app/session` — выход и отзыв. `GET` и `DELETE /api/app/sessions` — список устройств и удалённый отзыв (Settings → Account → «Устройства»).
* Оболочка хранит `deviceToken` в Keychain (iOS, доступность `AfterFirstUnlockThisDeviceOnly`) или в хранилище на базе Android Keystore. Если включена биометрия, токен выдаётся сайту только после Face ID / Touch ID / отпечатка.
* На сайте `store/crmApi.ts` в режиме приложения при 401 один раз пробует refresh через `utils/native/auth.ts`, повторяет запрос и только потом вызывает `sessionExpired()`. Обычный сайт работает как раньше.
* Биометрию предлагаем один раз после первого входа («Входить по Face ID?»), потом переключатель в Settings → Account.
* Проверить при реализации: есть ли у проекта второй фактор входа; если появится — сессия устройства обязана его учитывать.

## 8. Push-уведомления

Сегодня уведомления показывает колокольчик с опросом раз в 30 секунд и, при включённой настройке, системное уведомление браузера, пока вкладка открыта. В закрытом приложении push не придёт — нужен серверный канал.

* **Модель** `PushDevice`: user, platform, token (уникальный), shellVersion, locale, enabled, lastSeenAt.
* **Маршруты:** `POST /api/app/push` — зарегистрировать или обновить токен (вызывает оболочка после того, как человек разрешил уведомления); `DELETE /api/app/push` — при выходе или отключении.
* **Отправка:** `lib/push.ts` через FCM HTTP v1 (`https://fcm.googleapis.com/v1/projects/<проект>/messages:send`). OAuth-токен сервисного аккаунта берём тем же механизмом JWT-bearer,
  что уже работает в `lib/storage/firebase.ts` (`FIREBASE_SERVICE_ACCOUNT`), с областью `https://www.googleapis.com/auth/firebase.messaging`. Проверить: у сервисного аккаунта включён FCM API и есть нужная роль.
* **Точка подключения:** `lib/notify.ts`. `notify()` и `notifyMembers()` уже вызываются на все события (письмо, лид, сообщение канала, звонок, результат автоматизации). После `Notification.create` вызываем `sendPush(...)` без ожидания в критическом пути
  (ошибки не пробрасываем — так уже сделано для самого уведомления).
* **Кому:** тем, кому видно уведомление (`visibleTo`). **Фильтры:** настройки `User.notifications` (общий флажок push и «не беспокоить» `muteFrom`/`muteTo`, часовой пояс — `lib/timezone.ts`);
  дедупликация по `key`. Перед реализацией прочитать `components/crm/Settings/Notifications.tsx` и решить: общий флажок «не беспокоить» для e-mail и push (по умолчанию) или отдельный; в интерфейсе подписать явно.
* **Содержимое:** заголовок и текст на языке `PushDevice.locale`; в `data.url` — путь для перехода (только путь нашего хоста); бейдж на иконке = число непрочитанных (`unreadFor`).
  Всегда отправляем `notification` + `data` (data-only сообщения на Android не срабатывают в закрытом приложении).
* **Нажатие на push:** оболочка открывает `data.url` внутри WebView.
* **Чистка:** ответы FCM `UNREGISTERED` и `INVALID_ARGUMENT` — токен удаляем.
* **Настройка у владельца** (U4): проект Firebase с приложениями iOS и Android; **APNs Auth Key (.p8)** из кабинета Apple загружен в Firebase → Cloud Messaging; `GoogleService-Info.plist` и `google-services.json` лежат в репозитории оболочки.
* **Плагин:** `@capacitor-firebase/messaging` — единый FCM-токен на обеих платформах. Обычный `@capacitor/push-notifications` на iOS отдаёт токен APNs, а не FCM, и тогда серверу пришлось бы слать в APNs напрямую. Выбор подтверждается спайком в M4.3.
* **Ограничения, о которых честно говорим владельцу:**
  1. Дедлайны задач сегодня считает открытый браузер (`docs/PLATFORM.md`). Пока их не считает сервер, в закрытом приложении такого напоминания не будет.
     Нужен планировщик чаще суток: расписание GitHub Actions, дёргающее `/api/cron/reminders`, либо тариф Vercel Pro. Вне первого релиза (решение D12).
  2. Сообщения внутреннего чата и ленты сотрудников пока не серверные — уведомлений о них нет.
  3. Звонки (WebRTC через Twilio / SIP.js) работают только при открытом приложении: CallKit и ConnectionService не подключаем. Входящий звонок при закрытом приложении «не зазвонит».
  4. Проверять push нужно на **реальных** устройствах: на симуляторе iOS настоящая доставка через APNs недоступна.

## 9. Ссылки: в приложение, наружу, OAuth

### 9.1 Ссылки сайта, открывающиеся в приложении (Universal Links и App Links)

* `public/.well-known/apple-app-site-association` (без расширения, ответ `Content-Type: application/json` — через `headers()` в `next.config.js`) и `public/.well-known/assetlinks.json`.
  Нужны Team ID (Apple) и SHA-256 отпечатки подписи (Play App Signing и debug) — от владельца (U1, U2), до этого в файлах плейсхолдеры.
* Маршруты `/.well-known/*` middleware next-intl не трогает: его `matcher` исключает пути с точкой (проверено по `middleware.ts`).
* В AASA разрешаем все пути, кроме `/api/*` и `/_next/*`.
* В оболочке `App.addListener('appUrlOpen')`: если хост наш — переходим на путь внутри WebView, иначе игнорируем.

### 9.2 Внешние ссылки

Любая ссылка на чужой хост открывается в системном браузере через `openExternal`, а не в WebView (граница безопасности, раздел 13). В `capacitor.config.ts` `allowNavigation` — только наши хосты.

### 9.3 OAuth-подключения (Google, Microsoft, Meta, рекламные кабинеты)

Google запрещает OAuth во встроенных WebView (`disallowed_useragent`). Поэтому в приложении:

1. Маршрут вида `POST /api/…/oauth` возвращает `{ url }` (как `app/api/drive/oauth/route.ts`); сайт вызывает `openOAuth(url)` → системный браузер (SFSafariViewController / Chrome Custom Tabs).
2. При создании `state` в него кладётся признак `app=1`; финальная страница callback для такого `state` перенаправляет на `firmspace://oauth?ok=1`.
3. Оболочка ловит `firmspace://oauth`, закрывает браузер, сайт перезагружает раздел. Проверить на устройстве для каждого провайдера.

Не работает в WebView и не будет: **WhatsApp Embedded Signup** (всплывающее окно JS SDK). В приложении для такого подключения показываем подсказку «выполните на сайте в браузере» и не пытаемся обходить.

## 10. Файлы, камера, микрофон

* **Скачивание.** Схема `URL.createObjectURL` + `window.open` / `<a download>` в WKWebView и Android WebView ведёт себя иначе, чем в браузере (проверить на устройстве). Места в коде: `components/crm/Finance/download.ts`
  (три почти одинаковые функции — `downloadAct`, `downloadDeliveryNote`, `downloadDocumentPdf`), `components/crm/Collaboration/Documents.tsx`, `utils/avatar.ts`, `chatParts/useAttachmentUrls.ts` — всего 6 мест `createObjectURL` и 6 `window.open`.
  Сначала сводим три копии в `Finance/download.ts` к одной функции (полезно и для сайта), затем подключаем `saveAndOpen(blob, имя)` из `utils/native/files.ts`:
  в приложении — запись во временную папку и системное окно «Поделиться / Открыть в…», на сайте — как сейчас.
* **Загрузка файлов и фото.** `<input type="file">` в WebView работает через системные диалоги камеры и галереи; нужны строки разрешений (12.4). Проверить `capture`.
* **Микрофон.** Голосовые сообщения (`Collaboration/Chat.tsx`) и звонки требуют `getUserMedia`: на iOS — `NSMicrophoneUsageDescription`, на Android — `RECORD_AUDIO`. Проверить на устройстве, как ведёт себя Twilio / SIP.js в WebView.

### 11.3 CSS-правила (обязательные)

1. **Viewport:** `width=device-width, initial-scale=1, viewport-fit=cover` (в Next 13.4 через `metadata.viewport` строкой — экспорта `viewport` ещё нет; проверить в scratch-сборке). Высота экрана — `h-[100dvh]`, не `100vh`.
2. **Safe-area:** у всего, что прижато к краю (шапка, нижняя панель, боковые панели в ландшафте) — `env(safe-area-inset-top|bottom|left|right)`. На Android с target 35+ режим «от края до края» обязателен — без safe-area контент уедет под системные панели.
3. **Касание:** цель нажатия не меньше 44×44 px, между соседними — от 8 px.
4. **Поля ввода:** на телефоне шрифт не меньше 16 px, иначе iOS увеличивает страницу при фокусе.
5. **Без hover:** всё, что работает по наведению (подсказки, меню, кнопки действий в строках), должно иметь замену касанием.
6. **Таблицы:** на телефоне — карточки (ключевые поля) или контейнер с `overflow-x-auto`; горизонтальной прокрутки всей страницы быть не должно ни на какой ширине от 320.
7. **Фиксированные ширины:** от 500 px без `max-w-full` не допускаются.
8. **Модалки:** до `md` — на весь экран с собственной прокруткой; фон не прокручивается.
9. **Клавиатура:** поле ввода чата и формы остаются видны над клавиатурой (`interactive-widget=resizes-content` или `visualViewport`; режим `resize` плагина клавиатуры выбирается в M3.5, проверять на устройстве).
10. **Прокрутка:** `overscroll-behavior: none` на корневых прокручиваемых областях в режиме приложения; pull-to-refresh не нужен.
11. **Длинные строки:** ссылки и слова в чате и карточках — `break-words`; обрезка (`truncate`) не должна прятать единственную важную информацию.
12. **Тёмная тема:** новые цветовые классы → `node scripts/gen-dark-css.js`.
13. **Движение:** уважать `prefers-reduced-motion`.
14. **Ориентация:** телефоны — только портрет (оболочка блокирует), планшеты и складные — любая. CSS при этом не должен ломаться в ландшафте (для сайта и планшетов): проверка 844×390.
15. **Статус-бар** следует теме кабинета (светлая/тёмная): `utils/native/chrome.ts`.

### 11.4 Критерий «страница готова для мобильных» (Definition of Done)

Страница считается готовой, только если выполнено всё:

1. Нет горизонтальной прокрутки страницы на 320, 375, 412, 440, 600, 744, 834, 1024, 1194, 1376.
2. Цели нажатия ≥ 44 px, поля ≥ 16 px на телефоне, ничего не зависит от hover.
3. Модалки, выпадающие списки, тосты и подсказки не выходят за экран и не прячутся под клавиатурой или системными панелями.
4. Safe-area учтена: ничего не залезает под вырез, «остров» и жестовую полосу.
5. Светлая и тёмная темы выглядят нормально.
6. На 1440 и 1920 страница **не изменилась** (сравнение снимков до и после).
7. Проверено, а результат записан в журнал ROADMAP: чем именно (dev-сервер `:3210` с изменением размера окна, симулятор, реальное устройство) и что осталось непроверенным.

## 13. Безопасность

* `server.url` в релизных сборках — только `https://www.firmspace.de`; `cleartext` запрещён. Скрипт проверки релизной конфигурации в репозитории оболочки (`scripts/assert-release-config.mjs`) падает, если адрес не боевой, включён cleartext или отладка.
* `allowNavigation` — только наши хосты; всё остальное — системный браузер.
* **Мост Capacitor доступен любой странице в WebView.** Значит, XSS на нашем сайте открывает доступ к плагинам. Отсюда: минимум плагинов; `Filesystem` — только временная папка и документы приложения; CSP вводим сначала в режиме `Content-Security-Policy-Report-Only`,
  затем включаем (сайт использует Vercel Analytics, Stripe, Firebase, Google — список источников составить по факту).
* Токены: `deviceToken` в Keychain / Keystore, в базе — хеш, ротация, отзыв в Settings; JWT в `localStorage`, как на сайте (риск — XSS, отсюда CSP).
* Android: `allowBackup="false"`, `usesCleartextTraffic="false"`, отладка WebView выключена в релизе. iOS: App Transport Security без исключений.
* Ошибки: `ErrorReporter` → `/api/client-error` → Telegram уже есть; добавляем в отчёт признак приложения и версию оболочки.
* Закрепление сертификата не делаем: риск поломки при ротации сертификатов Vercel. Размытие экрана в переключателе приложений — необязательная задача на потом.

## 15. Выпуск и обновления

* **Изменения сайта** — как сейчас: ветка → «заливай» → `main` → Vercel. Приложения подхватывают их сами. Перед «заливай» для изменений мобильного режима: (а) 1440 и 1920 без изменений; (б) матрица ширин 11.5 для затронутых страниц; (в) для нативной части — просмотр в оболочке на симуляторе.
* **Изменения оболочки** (редко): новый плагин, разрешение, иконка, требования магазинов, нативная ошибка. Процедура: повысить `shellVersion` и номер сборки → собрать → TestFlight / Play Internal → чек-лист → отправка в ревью → после одобрения при необходимости поднять `minShellVersion`.
* **Каналы:** iOS — TestFlight (внутренний, затем внешний) → App Store. Android — internal → closed (12 тестировщиков × 14 дней для личного аккаунта) → production.
* **Тестовые сборки** (`staging`) указывают на адрес из переменной `CAP_SERVER_URL`. Preview-деплои Vercel могут быть закрыты защитой (SSO/пароль) — тогда для проверки использовать адрес dev-сервера в локальной сети (cleartext только в debug-сборке) или временно открыть preview. Релизная сборка жёстко на прод (раздел 13).
* **Срочная поломка сайта** — правка на сайте, эффект мгновенный. **Поломка оболочки** — новая сборка и ревью, сроки магазинов заранее не гарантируются.

## 16. Известные ограничения

1. Приложение требует сети: это тот же сайт. Без сети — локальная страница «нет соединения», данные офлайн не кешируются. Это действует до этапа 7; после него офлайн-ядро работает по разделу 18, всё остальное — только онлайн.
2. Звонки только при открытом приложении; входящий звонок при закрытом приложении не «зазвонит».
3. Напоминания о дедлайнах в закрытом приложении — только после серверного планировщика (8, D12).
4. Некоторые настройки (WhatsApp Embedded Signup, часть подключений) лучше выполнять в браузере на компьютере.
5. Ревью Apple по 4.2 — риск, а не гарантия (4.2).
6. Внутренний чат и лента сотрудников не серверные — push о них не приходит.
7. Админ-кабинет платформы (`/crm/admin`) для телефона не оптимизируем — только следим, чтобы он не ломался.

## 18. Офлайн-режим (этап 7)

Решения: D15 (SQLite), D16 (интерфейс без сети), D17 (охват и конфликты) — в ROADMAP. Делается после первого выпуска (оболочка 1.1); до этого действует 16.1. Правила — R21–R25.

### 18.1 Охват

| Раздел | Без связи |
|---|---|
| Контакты, компании, сделки, задачи, календарь | чтение, правка, создание |
| Заметки, комментарии и записи активности у сделок, контактов, компаний, задач | добавление |
| Фото и файлы к карточкам | очередь загрузки, до 25 МБ на файл |
| Заказы | только чтение (смена статуса запускает доставку и счета — онлайн) |
| Финансы, ПРРО, приём оплаты, отправка сообщений, почты и накладных, звонки, ИИ, реклама, интеграции, админ-кабинет, настройки | только онлайн: раздел показывает «нужна связь» |

Окно данных: открытые сделки и связанные контакты и компании; задачи со сроком от «сегодня минус 30 дней»; события ±60 дней; заказы за 90 дней. Мягкий лимит базы 200 МБ: вытесняется только кеш вложений, очередь правок — никогда.

### 18.2 Хранилище (D15)

* Нативная SQLite в приложении, один движок и для кеша, и для очереди правок. Кандидат — `@capacitor-community/sqlite` (SQLCipher); совместимость с Capacitor 8 и шифрование проверить в M7.3.
* Шифрование: ключ 256 бит генерируется при первом запуске и лежит в Keychain/Keystore (не выводится из пароля). Файл исключён из резервных копий iCloud и Android.
* Доступ только через `utils/native/db.ts` за интерфейсом `LocalStore`. Отдельная база на пару «пользователь + фирма» (`X-Org-Id`).
* Мост Capacitor медленнее IndexedDB на больших списках: читаем страницами, замеряем в M7.3 (3000 контактов). Если медленно — интерфейс `LocalStore` позволяет вынести кеш (не очередь) в другое хранилище по слову владельца.
* Шифрование влияет на экспортные декларации магазинов (Apple: `ITSAppUsesNonExemptEncryption`; Google) — учесть в M5.6 и M7.8.

### 18.3 Чтение

* Единая точка — `api()` и `apiCall()` в `store/crmApi.ts`. 13 файлов вызывают `fetch("/api…")` мимо неё: те, что относятся к 18.1, переводим на `api()` в M7.1.
* Таблица политик `utils/offline/policy.ts`: шаблон адреса → `cache` / `queue` / `online`. Чего нет в таблице — `online`.
* `cache`: при связи — запрос и обновление кеша; при отсутствии связи или сетевом сбое — ответ из кеша с пометкой «данные на …». Сегодня `api()` при любом сбое возвращает `null`: офлайн-слой обязан отличать «нет сети» от «ошибка сервера» и ошибку сервера кешем не маскировать.

### 18.4 Запись и очередь

* Правка из белого списка без сети (или при сетевом сбое) → запись в `outbox` и сразу в локальную копию: интерфейс видит изменение, запись помечена «ждёт отправки».
* Запись очереди: `clientMutationId` (UUID), `entity`, `op` (`create`, `update`, `delete`, `activity_add`, `upload`), `docId`, `fields`, `base` (значения этих полей, какими их видел пользователь), `createdAt`, `attempts`, `status` (`pending`, `sending`, `conflict`, `rejected`).
* Создание: `_id` формируется на устройстве (ObjectId, 24 hex); сервер принимает его только для сущностей из 18.1 и только если такого документа нет.
* Отправка: по порядку внутри документа; при появлении сети (`network.ts`), при возврате приложения на передний план, раз в минуту на переднем плане. Фоновая отправка (WorkManager, BGTask) — бонус, не гарантия.
* Ответы: 2xx — запись убирается, локальная копия заменяется ответом сервера; сетевой сбой или 5xx — повтор с нарастающей паузой, очередь не теряется; 401 — обновить сессию устройства (7); 4xx и 409 — запись уходит в «Проверить», очередь идёт дальше.
* При непустой очереди всегда виден индикатор «N изменений ждут отправки». Выход из аккаунта с непустой очередью — предупреждение с выбором «отправить сейчас» / «отказаться от изменений».
* Очередь привязана к пользователю и фирме: после смены аккаунта чужая очередь не отправляется.

### 18.5 Сервер (только обратно совместимые изменения; R6)

* Идемпотентность: заголовок `Idempotency-Key` = `clientMutationId`; коллекция `IdempotencyKey` (ключ, фирма, статус и тело ответа, срок 30 дней). Повтор возвращает сохранённый ответ: потерянный ответ не создаёт дубль.
* Обёртка `withSync(handler)` на маршрутах из 18.1: идемпотентность, приём `_id` при создании, проверка `base` при изменении (18.6). Бизнес-правила и права остаются в существующих обработчиках, не копируются.
* Побочные эффекты (карточка в ленте, уведомления коллегам, автоматизации `emit`) срабатывают при доставке, а не при вводе. Лента помечает «внесено офлайн в 14:32» по заголовку `X-Client-Time`; `createdAt` остаётся серверным.
* Дельта: `GET /api/app/sync/changes?since=<курсор>` отдаёт изменённые документы (по `updatedAt`, курсор с `_id` для одинаковых меток; у 41 из 43 моделей включены `timestamps`), удаления, `nextCursor`, `hasMore` и `resync: true`, если курсор старше срока хранения удалений. Фирма и права — теми же запросами, что в обычных списках.
* Удаления: сегодня почти везде жёсткие (мягкое удаление лишь у 3 из 43 моделей), поэтому модель `Tombstone` (фирма, сущность, `docId`, дата; хранение 90 дней), которую пишут маршруты удаления из 18.1.
* Тихий push «sync» (без данных, не чаще раза в минуту на устройство) при изменении данных фирмы, через `lib/push.ts` (8). Доставка на iOS не гарантирована, поэтому гарантированные триггеры — возврат в приложение, появление сети и опрос на переднем плане (как `utils/usePolling.ts`).

### 18.6 Конфликты (D17)

* Обнаружение по значению: правка несёт `base`; сервер применяет поле, только если текущее значение равно `base` (если оно уже равно новому — ничего не делает).
* Разные поля сливаются автоматически.
* Одно поле изменено с двух сторон: остаётся значение сервера, правка телефона уходит в «Проверить» («применить моё» / «оставить серверное»). Молча перезаписывать чужие изменения нельзя (R24).
* Исключения: заметки и комментарии — только добавление, конфликтов нет; «задача выполнена» побеждает.
* Перенос сделки по стадиям: если сервер уже переместил сделку (автоматизация, коллега), перенос с телефона — конфликт.
* Правка удалённого документа — отказ с причиной «запись удалена»; удаление документа, изменённого после `base`, — конфликт.

### 18.7 Безопасность

* Права проверяются на сервере при доставке каждой правки так же, как для онлайн-запроса: потерянный доступ → отказ в «Проверить».
* Отзыв устройства (7) или выход → локальная база и очередь стираются; после отзыва ничего не отправляется.
* В кеше только поля из 18.1: без реквизитов, платёжных и фискальных данных и токенов интеграций.
* Политика конфиденциальности, App Privacy и Data safety учитывают локальное хранение (M5.2, M5.6, M7.8).
* Сессия устройства на 90 дней (D5, M4.1) — обязательное условие: сегодняшний токен живёт сутки, и после дня без связи любая очередь упёрлась бы в 401.

### 18.8 Как открыть интерфейс без сети (D16, спайк M7.0)

SQLite решает только хранение данных. Сам сайт грузится с `server.url`, поэтому нужен отдельный способ показать интерфейс без сети.

* **(а) Service worker на живом сайте** (по умолчанию). Кеширует только неизменяемые `/_next/static/*` и оболочку по `NEXT_PUBLIC_BUILD`; данные CRM и ответы API — никогда. Сохраняет «один источник». На iOS service worker в WKWebView работает только для доменов из `WKAppBoundDomains` (до 10) при `ios.limitsNavigationsToAppBoundDomains`; это ограничивает переходы WebView вне списка (внешние ссылки и OAuth уже открываются системным браузером, 9). Проверено по документации и обсуждениям Capacitor 2026-09-30, на устройстве не проверялось; Android — проверить.
* **(б) Офлайн-мини-приложение в оболочке** (запасной вариант): вместо `www/offline.html` собранные экраны «Сегодня», «Контакты», «Сделки», «Задачи», «Новая заметка» читают SQLite. Работает на iOS, но дублирует часть интерфейса и обновляется выпуском оболочки — это исключение из R1, допускается только по слову владельца.

Итог спайка (что выбрано и чем проверено) записываем сюда.

### 18.10 Критерий готовности этапа 7

Проверять на реальных iPhone и Android; иначе «не проверено» (R11):

1. Режим полёта: создать, изменить, удалить, добавить заметку и фото.
2. Убить приложение с непустой очередью: очередь на месте.
3. Потеря ответа при отправке: дубля нет.
4. Одно поле изменено на телефоне и на сайте: запись в «Проверить»; разные поля: слиты.
5. Документ удалён на сайте, а на телефоне правился: отказ с причиной.
6. Два дня без сети, затем вход и отправка очереди.
7. Выход с очередью; смена фирмы; отзыв устройства (база стёрта).
8. Внешнее изменение (заказ с маркетплейса, вебхук) появилось после возврата сети.
9. 3000 контактов: первая синхронизация и скорость списков; заполненная память; сдвиг часов устройства.
