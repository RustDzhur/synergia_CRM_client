# Платформа для бухгалтеров и юристов (практики)

Решение (docs/TZ_MASTER.md §5): платформа — рабочий кабинет специалиста, а не его замена и не посредник. ИИ готовит черновики, подпись и ответственность — человека.

## Что есть (S3)
- **Практика** (`Practice`, `PracticeMember` с ролями partner / senior / junior / assistant) — открывается с обязательным акцептом договора обработки данных и обязательства о тайне (версия и время акцепта хранятся; тексты готовит юрист).
- **Связь с клиентом** (`ClientLink`): приглашение в обе стороны — практика создаёт токен, клиент вводит его; либо клиент вводит код практики, партнёр подтверждает и назначает сотрудников. Принимать и отзывать может только владелец или администратор фирмы клиента.
- **Роли в фирме клиента** `advisor` (бухгалтер) и `counsel` (юрист) — через `Membership.link`. Разделы — только `inventory`, `crm`, `tasks`, `collab` (`PRACTICE_GRANTABLE`); оплата, команда, настройки, автоматизация, почта и маркетинг не выдаются никогда. Роль нельзя назначить через «Команду».
- **Уровни доступа**: `read` — только чтение; `review` — чтение + `/api/review/*` (S4); `edit` — запись в выданных разделах. Реквизиты фирмы (`/api/finance/settings`) специалист не меняет ни на каком уровне.
- **Согласие** (`ConsentRecord`): создаётся при включении связи, отзывается при завершении; срок связи (`expiresAt`) закрывает доступ сам.
- **Немедленный отзыв**: проверка связи идёт на каждом запросе специалиста без кэша (`lib/practice/gate.ts`); завершение связи удаляет членства; уход сотрудника из практики закрывает его доступ ко всем клиентам.
- **Журнал доступа** (`AccessLogEntry`) виден клиенту: каждая запись — строкой, чтения — не чаще раза в 10 минут на раздел.
- Экран: Настройки → «Бухгалтер / юрист» (сторона клиента и сторона практики).

## Чего нет и почему
- Каталога специалистов и поиска исполнителей: юридическая квалификация посредничества не проверена.
- Комиссий с услуг специалистов и подписи отчётов платформой.
- ИИ над данными клиентов практики: режим по умолчанию `none`; включение — отдельное решение (S7).

## Работа бухгалтера (S4)
- **Закрытие периода** (`PeriodLock`, вкладка «Закрытие» в бухгалтерии): после закрытия сервер отклоняет (423) создание, правку и удаление счетов, расходов и банковских операций с датой в периоде — на уровне базы (`lib/finance/periodGuard.ts`), а не только в интерфейсе. Отметки, не меняющие учёт (ЭСФ, проверка, отправка), разрешены. Открыть период заново можно с обязательной причиной; всё остаётся в записи.
- **Проверка документов** (`/api/review/*`): `needs_review → approved | needs_fix`, пакетное одобрение, запросы клиенту («пришлите чек») с уведомлением и ответом. Специалист с уровнем `review` пишет только в эти маршруты.
- **Панель «Мои клиенты»** (`GET /api/practice/:id/dashboard`): по действующим связям сотрудника — неразнесённые операции банка, просроченные счета, документы на проверке/исправлении, открытые запросы, состояние закрытия, ближайший срок отчётности. Только агрегаты; каждое открытие панели пишется в журнал доступа клиента.
- **Сроки отчётности** (`lib/practice/deadlines.ts`) — данные с источником; срок для UZ помечен непроверенным (проверяет специалист). Праздничные переносы не учитываются.
- **Пакет «отдать бухгалтеру»** (`GET /api/finance/handoff?from=&to=`): ZIP с CSV-реестрами счетов, расходов и банка (для UZ — ещё реестры ЭСФ). DATEV для Германии остаётся в `/api/export?kind=datev` (формат подтверждает бухгалтер).

## Роботы и правила практики, юристу (S7)
- **Правила сверки** (`PracticeRule`): «контрагент/назначение содержит … → статья»; применяются при загрузке выписки и к неразмеченным движениям.
- **Пакеты «что сделает робот»** (`PracticeBatch`, `/api/review/batches`): предложение ничего не пишет → человек применяет → при необходимости откатывает весь пакет (записи, изменённые вручную после применения, не затираются; закрытый период пропускается). Это режим «спрашивать перед изменениями»: автоматического применения нет. ИИ в правилах не участвует, поэтому настройка «ИИ для данных клиентов практики» не затрагивается. Для Айрис и роботов с навыком «финансы» есть инструмент `propose_rules_batch` (с карточкой подтверждения).
- **Договоры** (`/crm/settings/legal`, `/api/legal/*`): версии (не перезаписываются), статусы `draft → in_review → approved | rejected → signed → archived` (подписанное не возвращается), срок → событие календаря, сравнение версий построчно, шаблоны с переменными `{{имя}}`, чек-лист проверки (памятка специалисту, не юридическое заключение). Текст ИИ (`aiDraft`, инструмент `save_legal_draft`) везде помечен «черновик для проверки специалистом».

## Дополнения по ТЗ §5
- **Пакет бухгалтеру** теперь по режиму рынка: DATEV (DE), книга доходов и реестр ПН (UA), реестры ЭСФ (UZ) + PDF выставленных счетов (до 200).
- **Комментарии с упоминаниями** (`/api/review/comments`): упомянуть можно только участника той же фирмы; он получает уведомление.
- **Журнал субподрядчиков** (`Subprocessor`, `/api/admin/subprocessors`; практики видят список в «Бухгалтер / юрист»). Список заполняет администратор платформы.
- **Коммерческие условия практики** (`/api/admin/practice-terms`, `PlatformSettings`): бесплатно до 3 клиентов, цена подписки и скидка клиенту — пусты, пока владелец их не задал. `enforce` по умолчанию выключен; включённый, он останавливает добавление 4-го клиента без подписки (`Practice.paidUntil`, ответ 402). Приём оплаты подписки не реализован.
- **Панель клиентов:** фильтры (поиск, «только с открытыми вопросами»).

## Не сделано (нужны внешние условия)
- Агрегатор открытого банкинга для Германии (finAPI и др.): нужен договор с агрегатором; собственная регистрация в BaFin не предполагается.
- Тексты договора обработки данных и обязательства о тайне — готовит юрист (в системе хранится версия и дата акцепта).
