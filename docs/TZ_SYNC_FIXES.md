# ТЗ: исправление сквозной синхронизации CRM ↔ задачи ↔ финансы и устранение найденных дефектов

Основание: глубокий аудит кода платформы (ветка `main`, коммит `7784c54`). Каждый пункт ниже подтверждён чтением кода, ссылки на файлы указаны. Что НЕ проверялось (запуск приложения, реальная БД, UI в браузере), отмечено в разделе 8.

Документ заменяет раздел «Найденные разрывы» из `docs/SYNC_BRIEF.md`: гипотезы G1–G11 оттуда здесь превращены в подтверждённые дефекты.

---

## 1. Цель

Любое изменение сущности (клиент, сделка, задача, заказ, счёт, платёж, договор, расход) отражается везде, где эта сущность показывается или учитывается: ленты, карточки, статусы, отчёты, уведомления, автоматизация. Данные одной фирмы не доступны тем, у кого нет прав. Деньги и номера документов не искажаются при повторах и параллельных запросах.

## 2. Как устроена система сейчас (факты)

- Next.js 13 App Router, Prisma/PostgreSQL, 50+ моделей, 243 API-маршрута. Клиент: отдельные zustand-хранилища (`store/use*Store.ts`).
- Связи между сущностями: строковые id без внешних ключей. В схеме `prisma/schema.prisma` нет ни одного `@@index` и `@@unique`. Деньги хранятся как `Float`.
- Изоляция фирм: поле `owner` (CRM-модели) или `org` (Finance-модели), проверяется в каждом запросе вручную. Помощники `ownedContact/ownedCompany/ownedDeal/ownedContract` в `lib/deals.ts`.
- Права: `lib/access.ts` → `moduleForPath()` определяет раздел по первому сегменту адреса API; проверка в `requireUser` (`lib/auth.ts`).
- Побочные эффекты: `emit()` в `lib/automation/emit.ts` (правила автоматизации), `notify()` в `lib/notify.ts`, `logAudit()`, лента `Activity` (`mkActivity` в `lib/activities.ts`). Вызываются вручную из каждого маршрута отдельно.

## 3. Реестр дефектов

Приоритеты: **P0** безопасность, юридическая корректность, потеря данных. **P1** нарушение сквозной синхронизации. **P2** надёжность и масштаб.

### P0

**D-01. Разделы API без проверки прав (fail-open).**
`lib/access.ts::moduleForPath` возвращает `null` (доступ любому участнику фирмы) для всех адресов, которых нет в `switch`. Не защищены: `bank`, `boms`, `pos`, `production`, `production-orders`, `purchases`, `reconciliation`, `recurring-invoices`, `stock`, `stock-docs`, `supplier-invoices`, `suppliers`, `warehouses`, `projects`, `issued-docs`, `import`, `export`, `assets`, `marketplace`, `calendar`, `ukrposhta`, `novaposhta`, `onedrive`, `messenger`, `whatsapp`, `webchat`, `media`, `messages`. Маршруты `bank/*`, `stock`, `suppliers`, `export` проверяют только `requireUser`.
Следствие: сотрудник с ролью `employee` (модули crm, tasks, collab, mail) и `viewer` (чтение) видит банковские счета и движения, склад, поставщиков, закупки, и может выгрузить `GET /api/export?kind=invoices|expenses|contacts` целиком. Для `employee` доступна и запись в незащищённых разделах.
Расположение проверки тарифа `featureForApi` (`config/plans.ts`) требует аналогичной проверки на тот же пробел (не проверено, см. раздел 8).

**D-02. Повторяющиеся номера счетов.**
`lib/finance/numbering.ts::nextNumber` — чтение счётчика из Json и запись обратно без блокировки и транзакции; на `Invoice.number` нет `@@unique([org, number])`. Два одновременных запроса получают один номер. Для счетов это юридическое нарушение (сплошная нумерация, §14 UStG / аналог для Украины).

**D-03. Повторная доставка webhook удваивает частичную оплату.**
`app/api/webhooks/pay/[provider]/[token]/route.ts`: защита от дубля только `if (inv.status === "paid")`. Для счёта со статусом `sent`/`overdue`, оплаченного частично, повторная доставка того же платежа вызывает `applyPayment` ещё раз и прибавляет сумму снова. У платежа нет сохранённого идентификатора провайдера.

**D-04. Удаление этапа воронки удаляет все сделки в нём.**
`app/api/stages/[id]/route.ts` DELETE: `prisma.deal.deleteMany({ stage })` без подтверждения, архива и учёта связей. Задачи (`Task.deal`), счета, заказы, КП, договоры, расходы, разговоры с этой сделкой остаются со ссылкой на несуществующую запись. Аналогично удаление самой сделки (`app/api/deals/[id]` DELETE), контакта и фирмы не проверяет зависимые записи.

**D-05. Склад: гонка при изменении остатка.**
`lib/finance/stock.ts::moveStock` читает `stockQty`, прибавляет в памяти, пишет обратно. Параллельные движения теряют друг друга. Списание и снятие резерва в `app/api/orders/[id]/route.ts` не в транзакции: сбой посередине оставляет склад и журнал рассогласованными.

**D-06. Расход принимает чужие ссылки.**
`app/api/expenses/route.ts`: `deal: b.deal`, `order: b.order`, `receipt: b.receipt` записываются без проверки `owned*`. Можно привязать расход к сделке другой фирмы по известному id (нарушение изоляции фирм).

### P1

**D-07. Оплата счёта реализована в четырёх местах с разным результатом.**

| Путь | Файл | `invoice_paid` в автоматизацию | Уведомление | Фискальный чек (ПРРО) | Остальное |
|------|------|:---:|:---:|:---:|-----------|
| Кнопка «оплачен» | `app/api/invoices/[id]/pay` | да | нет | да | аудит |
| Webhook эквайринга | `app/api/webhooks/pay/...` | да | да | **нет** | `paidVia`, аудит |
| Ассистент Айрис | `lib/finance/aiActions.ts::markPaid` | да | нет | да | дата оплаты, аудит |
| Сверка с банком | `app/api/bank/transactions` PATCH → `bookPayment` | **нет** | нет | **нет** | аудит; откат при отвязке |

В `aiActions.ts` комментарий прямо признаёт дублирование («правило должно меняться в обоих местах»). Платёж картой по украинской фирме не фискализируется. Отвязка банковского движения возвращает статус `sent`, но `paidAt` остаётся заполненным.
Частичная оплата не отправляет событий нигде.

**D-08. Финансовые события нигде не попадают в ленту клиента и сделки.**
`mkActivity` вызывается только в `app/api/deals/**`, `lib/ai/*`, `lib/leads*`, `lib/activities.ts`. Ни счёт, ни оплата, ни КП, ни договор, ни заказ, ни расход не пишут в `activities` сделки, контакта или фирмы. Смена этапа пишется только в ленту сделки, не контакта.

**D-09. Оплата не двигает сделку и заказ.**
`Deal.wonAt` ставится только вручную (`PATCH /api/deals/[id]`, поле `won`) или перетаскиванием на последний этап; нигде больше не читается для расчётов (только отображение в `DealsBoard` и фильтр `dealForCustomer`). У `Order` нет статуса «оплачен»: после оплаты счёта заказ остаётся `invoiced`. Подписание договора (`contracts/[id]/sign`) и принятие КП не двигают сделку, пока владелец не настроил правило автоматизации.

**D-10. Изменение и удаление клиента не распространяются.**
`PATCH /api/contacts/[id]` и `/api/companies/[id]` только обновляют сам документ. Копии в `Deal.clientName/contactName/companyName`, `Invoice/Quote/Order/Contract.customerName`, `Conversation.name`, `Contact.company` остаются старыми. `Contact.companyId` нигде не проверяется на принадлежность и не синхронизируется со строковым `Contact.company`. DELETE контакта/фирмы не проверяет неоплаченные счета и открытые сделки.

**D-11. Задачи не связаны с клиентом.**
`Task` имеет `deal`, но не имеет `contact`/`company`: в карточке контакта и фирмы задач нет. Выполнение задачи (`PATCH /api/tasks/[id]`) не пишет в ленту и не вызывает `emit` (есть только `task_created`). `PATCH` не умеет менять и снимать связь со сделкой (проверяется только `project`). Поле `responsible` — строка с именем (при создании подставляется `firstname`), не id участника: двое с одним именем неразличимы, адресное уведомление невозможно.

**D-12. Карточки клиента неполные.**
Карточка контакта показывает документы (`ContactDocuments` → `/api/contacts/[id]/documents`). Нет: задач, платежей и остатка к оплате, расходов, событий календаря. У карточки фирмы (`CompanyEdit.tsx`) панели документов нет совсем. Карточка сделки (`/api/deals/[id]/documents`) показывает КП/счета/заказы/договоры, но не платежи, расходы и маржу сделки (расходы с `Expense.deal` есть, в карточке не используются).

**D-13. Уведомления и сроки.**
- Предупреждения о сроках задач и сделок (`POST /api/notifications`) создаёт браузер, когда страница открыта: если у ответственного кабинет закрыт, уведомления нет. Уведомление уходит всей фирме (`user: null`), а не ответственному.
- Просрочка счёта (`lib/finance/overdue.ts`) вызывает только `emit`; уведомления участнику и записи в ленту нет.
- Крон один раз в сутки (ограничение тарифа Vercel Hobby, см. `docs/PLATFORM.md`).

**D-14. Автоматизация: пробелы и гонка.**
- Нет событий: `task_completed`, `contact_updated`, `company_updated`, `deal_won`, `invoice_partial_paid`, `bank_matched`, `expense_created`, `quote_accepted`.
- `lib/automation/index.ts::runDueJobs`: «атомарный claim» на деле `findFirst` + `update` — два параллельных опроса (разные вкладки/сотрудники) могут взять одно задание. Троттлинг `lastRun` хранится в памяти процесса и в serverless не работает между инстансами.

**D-15. Клиентское состояние не синхронизируется.**
15 отдельных zustand-хранилищ. Взаимное обновление реализовано только для действий ассистента (`store/aiRefresh.ts`). После обычного действия пользователя (оплатил счёт в «Финансах») открытая вкладка «CRM»/«Dashboard»/«Задачи» показывает старые данные до перезагрузки. Опрос раз в 30 секунд обновляет только уведомления.

**D-16. Видимость сделки не работает.**
`Deal.availableToAll` сохраняется и редактируется (`MoreCard.tsx`), но `GET /api/deals` возвращает все сделки фирмы любому участнику. Поле `responsible` — свободный текст.

**D-17. Заказ: нет конечного автомата.**
`PATCH /api/orders/[id]`: допустим любой переход между статусами `draft/confirmed/fulfilled/invoiced/closed/cancelled`. Откат из `fulfilled` не возвращает товар на склад, `cancelled` после `fulfilled` тоже. Отмена заказа не отражается на выставленном счёте.

### P2

**D-18. Нет индексов.** Все фильтры по `owner`/`org`, `Invoice.deal/contact/status/dueDate`, `Task.deal/owner`, `Deal.contact/stage`, `BankTransaction.account/matchType` выполняются полным сканированием. Рост данных приведёт к деградации.
**D-19. Деньги в `Float`.** Накопление погрешностей (`paidAmount`, `amount`, `value`). Нужны `Decimal` или целые минорные единицы. Округления разбросаны по коду.
**D-20. Дашборд читает всё.** `app/api/finance/dashboard` загружает все счета фирмы без фильтра по дате, суммирует без пересчёта валют (не проверено, требует подтверждения).
**D-21. Нет автоматических тестов** (`package.json`: только `dev/build/start/lint`, в CI только `tsc` и `build`). Регрессии в п. D-07, D-09 не ловятся.
**D-22. Два способа возврата ошибок и «молчащие» `catch`** в побочных эффектах: сбой уведомления/ленты не виден никому, кроме консоли.

## 4. Требования (рабочие пакеты)

Порядок выполнения: WP-0 → WP-1 → WP-2 → WP-3 → WP-4 → остальные. Каждый пакет — отдельная ветка/PR, зелёные `tsc`, `lint`, `build`, тесты пакета.

### WP-0. Безопасность и целостность (D-01, D-02, D-03, D-05, D-06)

1. **Default-deny прав.** `moduleForPath` по умолчанию возвращает «запрещено», а `null` («любой участник») — только для явного списка (`auth`, `health`, `notifications`, `orgs` кроме members, `public`, `client-error`, `contact`, `hooks`, `webhooks`, `cron`, `connect`, `media` по необходимости). Закрепить за разделами:
   `inventory`: `bank`, `boms`, `pos`, `production`, `production-orders`, `purchases`, `reconciliation`, `recurring-invoices`, `stock`, `stock-docs`, `supplier-invoices`, `suppliers`, `warehouses`, `issued-docs`, `export`, `import`, `assets` (разделить export/import по виду данных: `kind=contacts|companies` → `crm`, остальное → `inventory`);
   `tasks`: `projects`; `collab`: `calendar`, `messages`, `messenger`, `whatsapp`, `webchat`; `marketing`: `marketplace`; `settings`: интеграции доставки (`novaposhta`, `ukrposhta`, `onedrive`).
   Добавить автотест, который обходит все `app/api/**/route.ts`, и падает, если для первого сегмента нет явного решения в таблице (новый маршрут нельзя забыть).
2. Применить ту же таблицу к `featureForApi` (тарифы).
3. **Нумерация документов.** Добавить `@@unique([org, number])` для `Invoice`, `Quote`, `Order`, `Contract` (после проверки существующих дублей скриптом из WP-9). Счётчик увеличивать атомарно (`UPDATE ... SET counters = jsonb_set(...) RETURNING` либо отдельная таблица `DocCounter(org, key, seq)` с `upsert` и `increment`). При конфликте уникальности — повтор с новым номером (до 3 раз).
4. **Идемпотентность платежей.** Новая таблица `PaymentEvent(org, invoice, source, externalId, amount, createdAt)` с `@@unique([org, source, externalId])`. Webhook, банк, ручной и AI-путь регистрируют платёж через неё; повтор того же `externalId` возвращает `duplicate: true` и ничего не меняет. Для ручной оплаты `externalId` — id клиента-запроса (ключ идемпотентности из заголовка/тела) либо `manual:<invoice>:<timestamp-bucket>`.
5. **Склад.** `moveStock` — одна транзакция: `product.update({ stockQty: { increment: qty } })` + запись движения. Операции заказа (`releaseReserve`, `consumeForOrder`, смена статуса) — в одной транзакции со сменой статуса.
6. **Проверка ссылок расхода:** `deal`, `order` проходят через `ownedDeal`/проверку заказа своей фирмы; `receipt` — через проверку принадлежности файла фирме.

Критерии: сотрудник `employee` получает 403 на `/api/bank/*`, `/api/stock`, `/api/export?kind=invoices`; 20 параллельных `POST /api/invoices` дают 20 разных номеров; повторная доставка одного webhook не меняет `paidAmount`; 50 параллельных списаний дают остаток, равный сумме движений; расход с чужим `deal` отклоняется.

### WP-1. Единый слой платежей и событий (D-07, D-08, D-09, D-14)

1. Создать `lib/sync/payments.ts::registerPayment(org, invoiceId, { amount, source, externalId, paidAt?, actor?, via? })` — единственная точка учёта оплаты. Все четыре пути (D-07) вызывают только её. Внутри, в одной транзакции: `PaymentEvent` → пересчёт `paidAmount/status/paidAt` → затем побочные эффекты вне транзакции, каждый в `try/catch` с записью ошибки в журнал (не в консоль): `emit(invoice_paid | invoice_partial_paid)`, `notify` ответственному, фискальный чек (если нужен по `fiscalAdvice`, для всех источников), запись в ленту сделки/контакта/фирмы, `logAudit`, обновление заказа (`paid`) и сделки по правилу WP-1.3.
2. Обратная операция `revertPayment` (отвязка банковского движения): пересчёт суммы, `paidAt = null`, статус, запись в ленту, `logAudit`.
3. **Правило сделки при оплате** (настройка фирмы `FinanceSettings.autoWinDealOnPaid`, по умолчанию включено): если все неотменённые счета сделки (`kind=invoice`) оплачены полностью и она не в статусе «выиграна» — `wonAt = now`, запись `won` в ленте, событие `deal_won`. При `revertPayment` — не снимать автоматически, а предлагать в ленте.
4. Добавить статус заказа `paid` (аддитивно, существующие значения не менять): оплата счёта заказа переводит `invoiced → paid`.
5. **Единый помощник ленты** `lib/sync/feed.ts::logActivity(org, targets: {deal?, contact?, company?}, type, text, meta)` поверх `mkActivity` (новые типы `payment`, `invoice`, `quote`, `contract`, `order`, `expense`, `won`; ключ идемпотентности в `meta` исключает дубли). Вызывать из: создания/отправки/оплаты/просрочки/кредит-ноты счёта, КП (отправка/принятие), заказа (создание/статус), договора (подпись), расхода с привязкой, смены этапа сделки (в ленту сделки и контакта).
6. Новые события автоматизации (расширить `EVENTS` и `eventBucket`): `deal_won`, `task_completed`, `contact_updated`, `company_updated`, `invoice_partial_paid`, `bank_matched`, `expense_created`, `quote_accepted`. Старые не менять.
7. Просрочка (`sweepOverdueInvoices`) пишет в ленту и уведомляет ответственного по сделке.

Критерии: сценарий «создать контакт → сделка → счёт → оплата четырьмя способами по очереди (на разных счетах)» даёт одинаковый набор эффектов (таблица D-07 везде «да»); повтор не создаёт дублей; сделка автоматически «выиграна» при полной оплате; в ленте контакта, фирмы и сделки видна запись об оплате.

### WP-2. Согласованность клиентов и связей (D-04, D-10, D-16)

1. **Каскад имён.** `lib/sync/customer.ts::propagateCustomerRename(org, { contactId?, companyId? }, oldName, newName)`: обновляет копии имён в открытых сделках и в документах со статусом `draft`/`sent`, а также `Conversation.name`; оплаченные и закрытые документы не меняются (юридическая неизменность), факт смены пишется в ленту клиента.
2. **Охрана удаления.** Контакт/фирма: если есть неоплаченные счета или открытые сделки — `409` с перечнем; удаление после подтверждения: ссылки обнуляются (`contact = null`), `customerName` сохраняется. Сделка: если есть связанные неоплаченные счета/открытые задачи — предупреждение и выбор (архивировать/отвязать). Этап: нельзя удалить непустой этап, только перенести сделки в выбранный этап (параметр `moveTo`); массовое удаление сделок — убрать.
3. `Contact.companyId`: проверка через `ownedCompany`, синхронизация строки `company` с именем фирмы при выборе и переименовании.
4. Скрипт согласования `scripts/reconcile-links.ts` (идемпотентный; по умолчанию отчёт, `--apply` исправляет): осиротевшие ссылки (`Invoice.deal/contact/company/order`, `Task.deal/project`, `Expense.deal/order`, `Contract.deal`, `Conversation.contact`, `Deal.contact/company`), устаревшие копии имён, дубли номеров документов.
5. **Видимость сделок.** Реализовать `availableToAll=false`: сделку видят владелец фирмы, администраторы и участник, указанный ответственным. Для этого `Deal.responsible` дополнить полем `responsibleUser` (id участника, необязательное) с заполнением из имени там, где оно однозначно.

### WP-3. Задачи (D-11, D-13)

1. Аддитивно: `Task.contact`, `Task.company`, `Task.responsibleUser`, `Task.completedAt`. Заполнение: при создании из сделки — контакт и фирма сделки. Миграция данных для существующих задач со сделкой — в скрипте WP-2.
2. `PATCH /api/tasks/[id]`: смена и снятие `deal/contact/company` (с проверкой принадлежности), при `completed=true` — `completedAt`, `emit(task_completed)`, запись в ленты сделки/контакта/фирмы, уведомление автору; при возврате — `task_reopened`.
3. Уведомления о сроках задач и сделок создаёт сервер (`sweep` из опроса `/api/notifications` и из крона), адресно `responsibleUser`, а не браузер и не вся фирма. Ключ идемпотентности как сейчас (`deadline:...`).
4. Календарь: сроки задач, `Invoice.dueDate`, `Contract.endDate`, срок сделки показываются из серверного источника `GET /api/calendar/derived?from&to` (не из кэша store), с ссылкой на сущность.

### WP-4. Карточки и клиентское состояние (D-12, D-15)

1. Единый запрос «сводка клиента»: `GET /api/contacts/[id]/overview` и `/api/companies/[id]/overview` → сделки, задачи, документы, платежи (`PaymentEvent`), остаток к оплате, расходы по сделкам клиента, события календаря, последние записи ленты. Добавить панель в `CompanyEdit` и расширить `ContactEdit`.
2. Сводка сделки: платежи, расходы, маржа (оплачено − расходы), все связанные задачи.
3. Центральная инвалидация на клиенте: модуль `store/invalidate.ts` с `invalidate(entities: ("deals"|"contacts"|"companies"|"tasks"|"finance"|"notifications")[])`, подписанный на ту же логику, что `aiRefresh.ts`. Каждая мутация в хранилищах вызывает `invalidate` для затронутых сущностей (оплата → finance, deals, contacts; задача → tasks, deals; и т.д.). `aiRefresh` переписать на неё же.

### WP-5. Заказы и склад (D-17)

Конечный автомат статусов заказа в `lib/finance/orderStatus.ts` (таблица допустимых переходов); обратные переходы со стороны склада выполняют компенсирующие движения (`return`); отмена заказа с выставленным неоплаченным счётом — предлагает кредит-ноту/отмену счёта. Интерфейс показывает только допустимые переходы.

### WP-6. Автоматизация (D-14)

Атомарный claim: `updateMany({ where: { id, done: false }, data: { done: true } })` и обработка только при `count === 1`; троттлинг перенести в БД (`lastRunAt` на фирме) либо убрать, заменив claim. Расширенные события из WP-1.6 доступны в UI правил (`components/crm/Automation/config.ts`) и в переменных (`ALIASES`).

### WP-7. Производительность (D-18, D-20)

Индексы: `Deal(owner, stage)`, `Deal(owner, contact)`, `Deal(owner, wonAt)`, `Task(owner, deal)`, `Task(owner, completed, deadline)`, `Invoice(org, status, dueDate)`, `Invoice(org, deal)`, `Invoice(org, contact)`, `Order(org, deal)`, `Expense(org, deal)`, `BankTransaction(org, account, date)`, `BankTransaction(org, matchType)`, `Notification(org, createdAt)`, `Conversation(owner, contact)`. ## 5. Нефункциональные требования

- Миграции только аддитивные; перед любым `@@unique` — отчёт о дублях и ручное решение. Без потери данных. Применение на проде только по моему отдельному подтверждению.
- Все новые строки интерфейса — через `messages/*` на всех имеющихся языках.
- Обратная совместимость API: существующие поля ответов не убирать; новые добавлять.
- Каждый побочный эффект выполняется после основной транзакции, ошибка эффекта не откатывает основное действие, но фиксируется (WP-9.3).
- Ограничения тарифа Vercel (суточный крон) учитывать: всё срочное работает через опрос и серверные проверки при запросах, крон — только страховка.
