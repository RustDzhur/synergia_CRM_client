## 0. Роль и правила работы

Ты старший full-stack инженер проекта (Next.js 13 App Router, Prisma/PostgreSQL, TypeScript, zustand, next-intl). Работаешь на существующем коде, не переписываешь его с нуля.

**Жёсткие правила**

1. Сначала читаешь код, потом пишешь. Никаких предположений: каждый пункт ниже, помеченный «проверить», сначала подтверди или опровергни чтением кода, и только потом чини.
2. Один раздел за раз. После каждого: `npx tsc --noEmit`, `npm run lint`, `npm run build`, отдельный коммит с понятным сообщением на русском (стиль `feat(...)`/`fix(...)` как в `git log`).
3. Не ломай мультиарендность: каждый запрос к БД фильтруется по владельцу (`owner` в CRM-моделях, `org` в Finance-моделях; это один и тот же id фирмы). Любая ссылка на другую запись проверяется через `lib/deals.ts` (`ownedContact`, `ownedCompany`, `ownedDeal`, `ownedContract`).
4. Не ломай права доступа: `lib/access.ts` (модули) и `config/plans.ts` (тарифы). Если пользователь не видит модуль, синхронизация не должна показывать ему данные из него.
5. Любая ошибка побочного эффекта (запись в ленту, уведомление, автоматизация) не должна ронять основное действие пользователя. Образец: `lib/automation/emit.ts`.
6. Все тексты интерфейса: через `messages/*` (next-intl), на всех языках, которые уже есть в проекте. Никакого хардкода строк в компонентах.
7. Не удаляй и не меняй данные в проде. Миграции схемы только аддитивные (новые необязательные поля/индексы), без потери данных.
8. Не добавляй зависимости без необходимости. Не создавай PR, пока я не попрошу.

## 1. Что уже есть (проверено по репозиторию)

- Связи между сущностями **слабые**: строковые поля без внешних ключей (`Deal.contact`, `Deal.company`, `Invoice.deal/contact/company/order/contract`, `Task.deal/project`, `Expense.deal/order`, `Contract.deal`, `Conversation.contact`). Целостность держится только кодом.
- `Deal` хранит **копии** имён (`clientName`, `contactName`, `companyName`) рядом с id. Если переименовать контакт или фирму, копии в сделках устаревают. Проверить то же самое у `Invoice.customerName`, `Order`, `Quote`, `Contract.customerName`.
- Лента активности (`activities` Json) есть у `Contact`, `Company`, `Deal`, `Task`. Фабрика: `lib/activities.ts` (`mkActivity`, `activityHandlers`). Системные типы `stage` и `created` пишет только сервер.
- Автоматизация: `lib/automation/emit.ts` и `lib/automation/index.ts` (`fireEvent`). События уже вызываются из: сделок, контактов, задач, заказов, счетов (отправка, оплата, кредит-нота, просрочка, напоминание, повторяющийся), КП, договоров, календарных дедлайнов.
- `lib/deals.ts` → `dealForCustomer(...)`: счёт/договор, созданный в Finance без явной сделки, сам привязывается к свежей невыигранной сделке клиента.
- Крон: `/api/cron/automation` (просрочка, повторяющиеся счета, напоминания) и `/api/cron/reminders` (календарь, отложенные действия). Раз в сутки, плюс опрос через `/api/notifications`, пока кабинет открыт.
- Финансовый слой большой: `lib/finance/*` (invoices, orders, quotes, expenses, bank, dunning, fiscal, stock, production, purchases, reports).

## 3. Целевая архитектура: один центр событий вместо разбросанных вызовов

**Принцип:** любое значимое изменение сущности проходит через одну серверную функцию, которая делает все побочные эффекты. Сейчас это размазано по десяткам route-файлов.

Создай `lib/sync/index.ts` (не ломая существующие `emit`/`emitDeal`, а вызывая их изнутри):

```ts
// имена условные, подгони под стиль кода
export type SyncEvent =
  | { type: "contact.updated"; id: string; changed: string[] }
  | { type: "contact.deleted"; id: string }
  | { type: "company.updated"; id: string; changed: string[] }
  | { type: "deal.stage"; id: string; from: string; to: string }
  | { type: "deal.won" | "deal.lost"; id: string }
  | { type: "task.created" | "task.completed" | "task.reopened"; id: string }
  | { type: "quote.sent" | "quote.accepted"; id: string }
  | { type: "order.status"; id: string; status: string }
  | { type: "invoice.sent" | "invoice.paid" | "invoice.partial" | "invoice.overdue" | "invoice.credited"; id: string }
  | { type: "contract.signed"; id: string }
  | { type: "bank.matched"; txId: string; invoiceId: string }
  | { type: "expense.created"; id: string };

export async function sync(org: string, ev: SyncEvent, actor?: { userId: string; name: string }): Promise<void>;
```

Внутри `sync` для каждого события по таблице ниже (раздел 4) делаются:

1. **Запись в ленту** связанных сущностей (сделка, контакт, фирма) через `mkActivity`. Текст короткий, с номером документа и суммой; `meta` содержит тип и id для ссылки.
2. **Обновление связанных записей** (статусы, `wonAt`, копии имён).
3. **Уведомление** ответственному/владельцу через существующий `lib/notify*`.
4. **Автоматизация**: `emit(...)` существующих правил, без новых циклов (действия автоматизации не запускают правила).
5. **Всё в try/catch**, ошибка логируется, основное действие не падает.

Идемпотентность: повторный вызов с тем же событием (повторный webhook банка/платёжки, повторный клик) не должен дублировать записи ленты и уведомления. Для этого используй ключ (`Notification.key` уже есть) и проверку «уже записано» в `activities`.

## 4. Матрица синхронизации (что за что цепляется)

| Источник | Что должно произойти автоматически |
|----------|-------------------------------------|
| **Контакт изменён** (имя, email, телефон, фирма) | Обновить копии имён в открытых сделках, неоплаченных счетах/заказах/КП/черновиках договоров; `Conversation.name`; запись в ленту контакта. Не трогать уже отправленные/оплаченные документы (юридическая неизменность), только хранить в ленте факт смены. |
| **Контакт удалён** | Не оставлять осиротевшие ссылки: обнулить ссылку, сохранив `customerName`; запретить удаление, если есть неоплаченные счета (или потребовать подтверждение). |
| **Фирма изменена/удалена** | То же, что для контакта, плюс реквизиты (`code`, адрес, `paymentDays`, `creditLimit`) используются как значения по умолчанию в новых счетах/КП. |
| **Сделка создана** | Запись `created`; автопривязка контакта/фирмы; `emitDeal`. |
| **Сделка → другой этап** | Запись `stage` в ленту сделки **и** контакта; задачи этапа по правилам автоматизации; уведомление ответственному. |
| **Сделка выиграна** (`wonAt`) | Предложить/создать заказ или счёт из сделки (`app/api/deals/[id]/order`), если нет; закрыть напоминающие задачи по правилу; запись в ленту контакта и фирмы. |
| **Сделка проиграна/закрыта** | Открытые задачи сделки: спросить или пометить; незаплаченные черновики КП/счетов: пометить. |
| **Задача создана/выполнена** | Лента сделки **и** контакта/фирмы (после добавления связи G2); событие календаря по сроку; уведомление ответственному и автору при выполнении. |
| **КП отправлено/принято** | Лента сделки; принятое КП → заказ (`app/api/quotes/[id]/order`), сделка получает сумму. |
| **Заказ меняет статус** | Лента сделки; `invoiced` создаёт счёт; `shipped`/`delivered` двигают склад (`StockMovement`) и производство; уведомление. |
| **Счёт отправлен** | Лента сделки/контакта; срок оплаты в календарь; напоминания по `dueDate`. |
| **Счёт оплачен полностью** (вручную, webhook, банк, касса) | Статус `paid`, `paidAt`; запись в ленту сделки/контакта/фирмы; **сделка → выиграна**, если это финальный счёт; закрыть напоминания и дуннинг (`dunningLevel`); заказ → оплачен; фискальный чек, если включён; уведомление; **один и тот же путь для всех источников оплаты**. |
| **Счёт оплачен частично** | `paidAmount`, остаток виден в карточке клиента; статус «частично». |
| **Счёт просрочен** (`lib/finance/overdue.ts`) | Лента, уведомление, дуннинг по настройкам; метка в карточке клиента. |
| **Кредит-нота** | Связь с исходным счётом, корректировка сумм в отчётах, лента сделки. |
| **Банковская транзакция** | Автосопоставление со счётом по сумме/номеру/IBAN; найденное закрывает счёт через тот же путь, что ручная оплата; расходная транзакция предлагает создать `Expense`. |
| **Расход / закупка** | Привязка к сделке/заказу (поля уже есть), попадает в маржинальность сделки и в отчёты. |
| **Договор подписан** | Лента сделки; сделка двигается по правилу; счёт по графику, если задан. |

### Этап C. Центр событий
1. Реализуй `lib/sync/index.ts` по разделу 3.
2. Перенеси в него побочные эффекты из route-файлов по матрице раздела 4, **по одному источнику за коммит**. Приоритет: оплата счёта (все 4 пути приходят в одну функцию), смена этапа сделки, задача, изменение контакта/фирмы, банк.
3. Старые `emit`/`emitDeal` оставь, `sync` вызывает их.

### Этап D. Интерфейс и клиентский кэш
1. Карточка контакта и фирмы: вкладки/блоки со всем связанным: сделки, задачи, счета (с остатком к оплате), КП, заказы, договоры, расходы, переписка, события. Один источник данных, без дублирования запросов.
2. Карточка сделки: связанные задачи, счета, платежи, расходы и итоговая маржа.
3. После любой мутации инвалидировать кэш всех затронутых разделов (теги RTK/zustand), чтобы не нужна была перезагрузка страницы.
4. Дашборд (`components/crm/Dashboard`) и отчёты (`lib/finance/reports.ts`) считаются из тех же данных, что карточки, чтобы цифры везде совпадали.

### Этап E. Календарь, уведомления, автоматизация
1. Сроки задач, счетов (`dueDate`), договоров и КП появляются в календаре как производные события, а не копии.
2. Уведомления по ключевым событиям с ключом идемпотентности.
3. Проверь, что действия автоматизации не создают циклы.

### Этап F. Тесты и приёмка
В проекте нет тестового раннера. Не вводи тяжёлый фреймворк: используй лёгкие скрипты в `scripts/` на реальной локальной БД либо добавь `vitest` только если я разрешу. Минимальный набор сценариев (обязательно прогнать и показать вывод):

1. Создать контакт → сделку → задачу → счёт → отметить оплаченным → проверить: лента сделки и контакта, `wonAt`, статус заказа, уведомление, отсутствие дублей при повторной отметке.
2. Изменить имя контакта → копии в открытых сделках и неоплаченных документах обновились, в оплаченных нет.
3. Оплата через webhook, вручную и через банковскую транзакцию дают **одинаковый** результат.
4. Удаление контакта с неоплаченным счётом блокируется или не оставляет осиротевших ссылок.
5. Сотрудник без доступа к финансам не видит суммы в ленте и карточке.
6. Два разных фирмы-арендатора: ни один побочный эффект не пересекает границу `owner`/`org`.

## 6. Критерии готовности (Definition of Done)

- [ ] Любое изменение клиента отражается в сделках, документах, переписке и ленте без перезагрузки страницы.
- [ ] Любой способ оплаты счёта приводит к одному и тому же набору эффектов.
- [ ] Нет осиротевших ссылок и устаревших копий имён (отчёт скрипта согласования пустой).
- [ ] Карточки клиента/сделки показывают все связанные сущности; цифры в дашборде, отчётах и карточках совпадают.
- [ ] Повторные события не создают дублей (идемпотентность).
- [ ] Права доступа и тарифы соблюдены, данные фирм не пересекаются.
- [ ] `tsc`, `lint`, `build` чистые; все тексты переведены; написан `docs/SYNC.md` (как это устроено, как добавить новое событие).
