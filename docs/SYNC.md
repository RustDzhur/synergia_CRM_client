# Сквозная синхронизация: как это устроено

Изменили клиента, сделку, задачу, счёт или платёж в одном месте — это отражается везде, где эта сущность показывается или учитывается. Здесь описано, как это сделано и как добавлять новое. Список исправленных дефектов — в `docs/TZ_SYNC_FIXES.md`.

## Принципы

1. **Одна точка на действие.** Оплата счёта, смена статуса заказа, правка клиента проходят через одну функцию в `lib/sync/*` и `lib/finance/*`; маршруты API, действия ассистента Айрис и webhook вызывают её, а не копируют правила.
2. **Побочные эффекты после основного действия и по отдельности.** Лента, уведомление, автоматизация, чек ПРРО выполняются после фиксации; сбой одного не отменяет остальное и не пропадает: он пишется в журнал (`AuditLog`, `action = "sync.error"`, см. `lib/sync/errors.ts`).
3. **Идемпотентность.** Повтор события (повторный webhook, двойной клик, повторная привязка банковской строки) ничего не меняет: платежи — по `PaymentEvent (org, source, externalId)`, записи ленты — по `key`, уведомления — по `Notification.key`.
4. **Данные фирмы не пересекаются.** Любая ссылка на запись проверяется на принадлежность фирме (`lib/deals.ts`: `ownedContact/ownedCompany/ownedDeal`).
5. **Права закрыты по умолчанию.** Новый адрес API без раздела недоступен никому (`lib/access.ts`).

## Карта модулей

| Модуль | Что делает |
|--------|-----------|
| `lib/sync/payments.ts` | `registerPayment` / `revertPayment`: единственная точка учёта оплаты. Блокировка строки счёта, `PaymentEvent`, статус, `paidAt`; затем автоматизация, уведомление, лента, чек ПРРО, заказ → `paid`, сделка → выиграна |
| `lib/sync/feed.ts` | `logActivity`: атомарная запись в ленту сделки / контакта / фирмы / задачи (jsonb `||`), с ключом идемпотентности |
| `lib/sync/documents.ts` | `logDocEvent`: событие счёта, КП, заказа, договора в ленты клиента |
| `lib/sync/customer.ts` | Каскад имён при правке клиента, охрана удаления (неоплаченные счета блокируют), снятие связей при удалении клиента и сделки, привязка контакта к фирме |
| `lib/sync/people.ts` | «Ответственный» словами → участник фирмы; видимость закрытых сделок (`dealScope`) |
| `lib/sync/deadlines.ts` | Серверный обход сроков задач и сделок, адресное уведомление ответственному |
| `lib/sync/overview.ts` | Сводка клиента и сделки: документы, оплаты, остаток, расходы, маржа по валютам |
| `lib/sync/revision.ts` | Ревизия данных фирмы для живого обновления интерфейса |
| `lib/finance/orderStatus.ts` | Таблица переходов статусов заказа; склад двигается в одной транзакции со статусом |
| `lib/finance/numbering.ts` | Номер документа: один `UPDATE … RETURNING`, без повторов |
| `store/invalidate.ts` | Шина обновления в браузере: запись в одном разделе перечитывает затронутые хранилища |

## Что происходит при оплате счёта

Любой путь — кнопка «оплачен», webhook эквайринга, ассистент, привязка банковской строки — вызывает `registerPayment`:

1. Транзакция: блокировка счёта → проверка статуса → `PaymentEvent` → `paidAmount`, `status`, `paidAt`.
2. Запись в ленту сделки, контакта и фирмы («Счёт … оплачен»).
3. Событие автоматизации `invoice_paid` (или `invoice_partial_paid`).
4. Уведомление фирме.
5. Полная оплата: заказ `invoiced → paid`; сделка → «выиграна», если оплачены все её счета (настройка фирмы `FinanceSettings.autoWinDealOnPaid`, по умолчанию включена; ручная отметка главнее); чек ПРРО при включённой автофискализации.
6. Запись в журнал действий.

Отмена платежа (`revertPayment`) возвращает сумму и статус, снимает `paidAt`, пишет в ленту.

## Как добавить новое событие синхронизации

1. Добавьте тип в `EVENTS` (`lib/automation/index.ts`) и в `components/crm/Automation/config.ts`; подпись `ev_<тип>` — в `messages/{de,en,ua}.json`; при необходимости — корзину переменных в `eventBucket`.
2. В месте, где событие происходит, после основного действия вызовите `emit(org, { type, data })` и, если оно должно быть видно в карточках, `logActivity` / `logDocEvent` с ключом идемпотентности.
3. Если событие меняет данные, которые показывает другой раздел, добавьте путь API в `AFFECTS` (`store/invalidate.ts`).
4. Добавьте тест в `tests/` (запуск: `DATABASE_URL=… npm test`).

## Как добавить маршрут API

Первый сегмент адреса должен быть в `moduleForPath` (`lib/access.ts`) и, если раздел входит в тариф, в `featureForApi` (`lib/features.ts`). Если нет — маршрут закрыт для всех, а `tests/access.test.ts` падает. Публичные хуки без `requireUser` перечисляются в `OPEN_API_SEGMENTS`.

## Применение изменений схемы

Автоматически схема не накатывается (`prisma db push` — вручную). Этот набор изменений **аддитивный**, но содержит уникальные индексы на номера документов (`Invoice`, `Quote`, `Order`, `Contract`: `@@unique([org, number])`). Перед применением на рабочей базе:

```bash
node scripts/reconcile-links.mjs          # отчёт: осиротевшие ссылки, устаревшие имена, ДУБЛИ НОМЕРОВ
node scripts/reconcile-links.mjs --apply  # безопасное исправление (код 2 — остались дубли номеров)
npx prisma db push                        # если дубли номеров есть, он остановится: разберите их с бухгалтером
```

Перенумеровать выпущенные счета нельзя (сплошная нумерация), поэтому дубли скрипт только показывает.

## Тесты

`npm test` (vitest). Интеграционные тесты идут на настоящей PostgreSQL по `DATABASE_URL` и пропускаются без неё; в CI база поднимается сервисом (`.github/workflows/ci.yml`, задача `test`; выкладка ждёт и её). Каждый тест создаёт свою фирму, чистить базу не нужно.
