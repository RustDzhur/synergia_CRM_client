# Единое ТЗ: выкладка синхронизации, Робот-офис без кода, интеграции через Айрис, узбекский рынок, платформа для специалистов, банки-партнёры, позиционирование

Версия 1 от 2026-10-08. Это решающий документ: в нём нет вариантов, а есть принятые решения. Подробности и источники — в трёх предыдущих ТЗ: `TZ_SYNC_FIXES.md` (сделано), `TZ_UZBEKISTAN_AND_ROBOTS.md`, `TZ_PROFESSIONALS_BANKS_POSITIONING.md`. Если что-то здесь противоречит им, действует этот документ.

## 1. Что делаем и в каком порядке

Один исполнитель, спринты по 2 недели, каждый спринт заканчивается рабочим результатом, тестами, сборкой и проверкой в браузере.

| Спринт | Результат | Условие входа |
|---|---|---|
| **S0** | Синхронизация выложена на сервер | вы применили схему на базе (раздел 2) |
| **S1** | Рынки перестают быть `DE\|UA` в коде (реестр профилей). Каталог ролей роботов и платформенные роботы лежат в данных; платформенные роботы закрыты для чужих фирм на сервере | S0 |
| **S2** | Узбекский язык `uz` и режим рынка UZ версии 1 (бета) | S1 |
| **S3** | «Практика»: роль специалиста, связь с клиентом, журнал доступа, единые согласия | S1 |
| **S4** | Панель «Мои клиенты», проверка документов, запросы клиенту, закрытие периода | S3 |
| **S5** | Подключение интеграций через Айрис: реестр паспортов, инструменты, защищённая форма ключей | S1 |
| **S6** | Банки: единый коннектор, перенос monobank и ПриватБанка, страница и кабинет банка-партнёра, реферальная атрибуция | S3 (согласия) |
| **S7** | Роботы и правила практики, инструменты юриста, агрегатор для Германии | S4, S6 |
| **S8** | UZ версия 2: готовые модули по официальной документации API — Payme, Click (приём оплаты), Didox и Faktura.uz (ЭСФ), онлайн-касса. Каждый пользователь подключает **свой** аккаунт со своими ключами; платформа даёт максимально подготовленные инструменты (§6.4) | документация API провайдеров; тестовые ключи — только для снятия статуса `beta` |

Срок: S0 — 1 неделя (в основном ваши действия), S1–S7 — около 25 недель работы одного исполнителя; S8 — по модулям, по мере готовности документации.


## 2. S0. Выкладка синхронизации (делается первой)

1. Вы на рабочей базе: `node scripts/reconcile-links.mjs` → отчёт; `--apply` → безопасное исправление; **дубли номеров счетов вы отдаёте бухгалтеру** (перенумеровывать выпущенные счета нельзя). `npx prisma db push` накатывает схему.
2. Я перевожу PR #5 из черновика после зелёного CI и сливаю по вашему слову.
3. После выкладки: проверка `/api/health`, пробный счёт, оплата, сверка банка.
4. Откат: схема аддитивная, код откатывается возвратом `deploy` на предыдущий коммит; данные не теряются.
5. С этого момента **`main` всегда выкладываемый**: одна задача — один PR, в PR есть тесты и документация, слияние только после зелёного CI.

## 3. S1. Фундамент

### 3.1. Реестр рынков
- `Market` — строка, профиль регистрируется в реестре (`registerMarket`); профиль = данные (валюта, язык документов, вкладки, документы, интеграции, налоговые модули, возможности) + необязательный модуль правил.
- Все проверки вида `country === "UA"` заменяются обращением к профилю. DE и UA после замены ведут себя как раньше: регрессионные тесты на документы, налоги, вкладки обязательны.
- `FinanceSettings.country` допускает `DE`, `UA`, `UZ`. Смена страны не удаляет данные: чужое скрывается.

### 3.2. Робот-офис
- **Решение:** каталог ролей хранится в базе (`RobotTemplate`), не в коде. Текущие 13 ролей загружаются сидом один раз; `lib/office/templates.ts` остаётся только сидом. Администратор платформы создаёт, правит и отключает роли в кабинете без деплоя; названия и описания хранятся в записи на `de, en, ua, uz`.
- **Решение:** роботы и поручения переносятся из `SectionRecord` в таблицы `Robot` и `RobotTask` (индексы `(org, status)`, `(org, robot)`), миграция идемпотентная, с проверкой количества записей до и после и откатом.
- **Решение:** платформенные роботы (Rex, Sven, Ada) переезжают в реестр `PlatformAgent`; их источники сигналов (cron `agentwatch.py`, Docker-агент) — необязательные адаптеры, настраиваются переменными окружения. На установке без них роботы не создаются, ошибок нет.
- **Решение:** везде, где маршрут `/api/office/*` или Айрис принимает id робота или поручения, действует проверка «платформенный робот виден и доступен только администратору платформы». Для остальных ответ 404. Тест: фирма B не читает, не правит, не увольняет, не даёт поручений, не получает в ответах Айрис роботов платформы фирмы A.
- Каталог фильтруется по рынку фирмы. Для UZ — свои роли (бухгалтер ЭСФ, кладовщик ЭТТН, платежи Payme/Click, поддержка на узбекском).

## 4. S2. Узбекский язык и рынок UZ

### 4.1. Язык
- **Решение:** `uz` — только латиница. Кириллица узбекского в версию 1 не входит. Обоснование: официальный курс — латиница, закон об обновлении алфавита в процессе принятия, объём ×2 не оправдан без спроса.
- Добавляется во все точки: `middleware.ts`, `languages/languages.ts`, `i18n.ts`, переключатель, метаданные, `sitemap`, `messages/uz.json` (полный набор ключей, около 3 700), документация, лендинг, PDF, письма, роли роботов, язык ответа Айрис.
- Перевод: я делаю черновик целиком. Язык выходит в интерфейсе с пометкой «перевод проверяется» и **не выбирается по умолчанию** для новых фирм, пока носитель не вычитал бухгалтерские и юридические термины. Скрипт `check-locales` расширяется на `uz`.
- Орфография и набор апострофов вынесены в нормализатор, чтобы смена алфавита не требовала переписывать файл.

### 4.2. Режим UZ версии 1 (бета) — жёсткий объём
**Входит:**
1. Профиль `UZ`: валюта `UZS`, часовой пояс `Asia/Tashkent`, язык документов `uz` + `ru` (двуязычный PDF), вкладки как в UA без украинских интеграций.
2. Реквизиты фирмы: наименование, ИНН, ПИНФЛ (14 цифр, проверка формата), код плательщика НДС, банк, счёт, МФО, адрес, руководитель, главный бухгалтер, система налогообложения, дата постановки плательщиком НДС. **Длина ИНН не подтверждена источниками: проверка только на цифры, под полем предупреждение «формат не проверен», пока специалист не подтвердит.**
3. Налоговые правила таблицей `TaxRule` с датами действия, ссылкой на источник и отметкой `verifiedBy`. Начальные записи по найденным источникам: НДС 12 %; добровольный упрощённый НДС 6 % без зачёта входного (с 01.06.2026 по 01.01.2030, торговля, общепит, услуги); экспорт 0 %; порог обязательной регистрации НДС ≈ 12 000 БРВ (≈ 5 млрд сумов с 01.06.2026); налог на прибыль 15 %. Каждая запись с пометкой `verifiedBy = null`, в интерфейсе под суммой НДС — предупреждение. Документ считается по правилу **на дату документа**.
4. Документы: счёт на оплату, акт выполненных работ, накладная, договор — на `uz` и `ru`, подписи руководителя и главного бухгалтера, нумерация, суммы в сумах с копейками, валютные документы с курсом ЦБ Узбекистана на дату документа (курс фиксируется, не пересчитывается задним числом).
5. **ЭСФ и ЭТТН в версии 1: готовим данные, не отправляем.** Система собирает все обязательные реквизиты ЭСФ (по Положению о счетах-фактурах), проверяет полноту и выгружает таблицу/файл для загрузки в кабинет оператора ЭСФ и печатную справочную форму с пометкой «не является ЭСФ». Отправка оператору — S8.
6. Курсы валют ЦБ Узбекистана (публичный источник, XML/JSON).
7. Журналы выданных и полученных счетов-фактур как реестры внутри системы.

**Не входит в версию 1 (это решение, а не откладывание без причины):**
- отправка ЭСФ/ЭТТН оператору и подпись ЭЦП (нет договора и документации API оператора);
- онлайн-касса и фискальные чеки;
- приём платежей Payme/Click/Uzum (нет договоров с провайдерами);
- проводки и план счетов НСБУ (до подтверждения специалистом раздел скрыт);
- подача отчётности в налоговые органы;
- автозаполнение по ИНН (публичного API не найдено).

### 4.3. Правовой контроль
- Пока ни одна запись `TaxRule` и ни один шаблон документа не имеют `verifiedBy`, в UZ-интерфейсе висит заметная плашка «Бета: правила не проверены специалистом Узбекистана».
- **Моя позиция:** выпускать UZ как общедоступный режим можно только после разовой проверки внешним бухгалтером или налоговым консультантом по чек-листу из `TZ_UZBEKISTAN_AND_ROBOTS.md`, раздел 10. Стоимость — разовый платёж внешнему специалисту, ориентир — один–три рабочих дня. Без неё UZ остаётся бетой для пилотов.
- Любое изменение закона вносится новой записью в `TaxRule`, а не правкой кода.

## 5. S3–S4. Платформа для бухгалтеров и юристов

### 5.1. Позиция
Платформа — рабочий кабинет специалиста, а не его замена. ИИ готовит черновики, подпись и ответственность — человека. Платформа не оказывает бухгалтерские и юридические услуги и не является посредником.

### 5.2. Что строим
1. **Практика.** Сущности `Practice`, `PracticeMember` (роли `partner`, `senior`, `junior`, `assistant`), `ClientLink` (практика ↔ фирма клиента: статус, область модулей, права `read | review | edit`, срок, кто пригласил, кто подтвердил, причина завершения).
2. **Роли в фирме клиента:** `advisor` (бухгалтер) и `counsel` (юрист) — через существующий `Membership` с ограниченными модулями; не могут менять тариф и оплату платформы, владельцев и удалять фирму. Роли добавляются в `lib/access.ts` и тесты карты прав.
3. **Согласия.** Единая таблица `ConsentRecord` (кому, зачем, что, срок, отзыв). Доступ специалиста работает только через действующее согласие; отзыв закрывает доступ немедленно.
4. **Журнал доступа специалиста** виден клиенту.
5. **Панель «Мои клиенты»:** неразнесённые операции, просрочки, расхождения, документы на проверку, ближайшие сроки отчётности по рынку, состояние закрытия, последняя активность; фильтры, массовые действия.
6. **Проверка:** статусы `draft → needs_review → approved | needs_fix`, пакетное одобрение совпавших с выпиской, запросы клиенту («пришлите чек»), комментарии с упоминаниями.
7. **Закрытие периода:** `PeriodLock`; после закрытия правка документов и операций периода запрещена **на сервере для каждого маршрута записи финансовых сущностей**; исправления — только сторно/корректировочный документ; повторное открытие — специалистом или владельцем с обязательной причиной и записью в журнал.
8. **Пакет «отдать бухгалтеру»:** выгрузка за период по режиму рынка (DATEV для DE, реестры и книга доходов для UA, реестры ЭСФ для UZ) + ZIP документов.
9. **Роботы и правила практики (S7):** `PracticeRule` («такой контрагент → такая статья», «такое назначение → такой счёт») применяются при сверке выписок и роботами практики; роботы практики работают только в режиме «спрашивать перед изменениями» и выдают отчёт «что сделал робот» с откатом пакета.
10. **Юристу (S7):** хранилище договоров клиента с версиями и статусами согласования, шаблоны с переменными, напоминания о сроках в календарь, сравнение версий, чек-лист проверки; ИИ-текст всегда помечен «черновик для проверки специалистом».
11. **Профессиональная тайна (для DE это условие запуска):** при регистрации практики обязательный акцепт договора обработки данных и обязательства о сохранении тайны (тексты готовит юрист, платформа хранит акцепт с версией и датой); настройка «ИИ для данных клиентов практики»: по умолчанию публичные ИИ-сервисы запрещены, режим «без ИИ» доступен; журнал субподрядчиков.

### 5.3. Что **не** делаем в версии 1 (решение)
- **Каталог специалистов и поиск исполнителей** — нет. Причина: юридическая квалификация посредничества не проверена, а ценность без базы практик нулевая. Вместо него — приглашение «своего» специалиста клиентом и клиентов практикой.
- **Комиссии с услуг специалистов** — нет.
- Подпись отчётов и заключений платформой — нет.

### 5.4. Коммерческие значения по умолчанию
Тариф «Практика»: кабинет бесплатный до 3 клиентов; с 4-го клиента — фиксированная подписка практики; клиенту при оплате через практику — скидка на тариф. **Числа — стартовые значения, хранятся в `PlatformSettings` и меняются без деплоя; окончательные цены вы устанавливаете сами.** Белая метка (домен, логотип) — платная опция тарифа практики во второй очереди.

## 6. S5. Подключение интеграций через Айрис

### 6.1. Позиция
Айрис ведёт подключение и делает автоматически всё, что можно сделать без человека. Ключи получает человек в кабинете провайдера, OAuth подтверждает человек, договоры подписывает человек. Это записывается в интерфейсе честной формулировкой «Айрис проведёт и сделает всё, что можно без вас».

### 6.2. Реализация
1. **Реестр паспортов** `IntegrationManifest` в базе: идентификатор, вид, рынки, названия и описания на 4 языках, поля (секретные отдельно), шаги «где взять ключ», проверочный запрос, правила вебхука, возможности, версия, статус `available | beta | planned`, источник.
2. **Универсальный коннектор** для простых REST/JSON-сервисов по паспорту без нового кода; сложные (JSON-RPC Payme, OAuth, подпись ЭЦП) — модули кода, но тоже заводятся паспортом. Закрытое объединение `IntegrationType` заменяется данными.
3. **Инструменты Айрис:** `find_integration`, `explain_integration`, `start_integration`, `verify_integration`, `finish_integration`, `list_my_integrations`. Записывающие инструменты всегда с карточкой подтверждения; если в контексте был чужой текст (письмо, документ), подтверждение обязательно в любом режиме.
4. **Защищённая форма секретов:** отдельное окно вне чата; значение уходит прямо на сервер маршрутом `/api/integrations/secrets`, шифруется, модель и журнал ИИ получают только «ключ сохранён и проверен»; ошибки провайдера очищаются от значений.
5. **Сценарий-эталон:** «хочу принимать оплату картой» → рынок фирмы → подбор провайдера → объяснение, что нужен договор → защищённая форма → проверка в песочнице → подтверждение → вебхук → правило «оплата пришла → счёт оплачен» (через `registerPayment`).

### 6.3. Статусы интеграций UZ (жёстко)
`available`: курс ЦБ Узбекистана, Telegram, электронная почта. `beta` (подключить можно, плашка «не проверено на живых ключах»): Payme, Click, Didox, Faktura.uz — модули написаны по официальной документации. `planned` (кнопка не показывается): Uzum, ATMOS, онлайн-касса, банки Узбекистана. Статус `beta` → `available` только после теста на живых тестовых ключах, которые пользователь или владелец получает у провайдера.

### 6.4. Принцип S8: человек подключает сам, мы готовим инструменты
Договор с Payme/Click/Didox/Faktura.uz заключает сам пользователь (или его бухгалтер); ключи — его. Платформа для каждого провайдера даёт: (1) модуль по официальной документации API (не общий «конструктор»); (2) паспорт с пошаговой инструкцией, где взять ключи, и адресами, которые нужно вписать в кабинет провайдера (callback/webhook, подставляется автоматически); (3) защищённую форму ключей; (4) кнопку «проверить подключение» и тестовый режим провайдера там, где он есть; (5) понятные сообщения об ошибках провайдера; (6) автоматическое следствие: оплата пришла — счёт оплачен (`registerPayment`), ЭСФ подготовлена — отправляется в кабинет оператора после подтверждения пользователя.

## 7. S6. Банки как партнёры

### 7.1. Позиция
Банк получает канал привлечения и удобную интеграцию, но **не получает данных клиентов без согласия** и не получает эксклюзивности. Свою лицензию платёжного провайдера не оформляем.

### 7.2. Что строим
1. **Единый коннектор банков:** интерфейс `BankProvider` (`capabilities`, `connect`, `listAccounts`, `statement`, `balance`, `webhook`, опционально `initiatePayment`). Адаптеры monobank и ПриватБанка переводятся на него без изменения поведения (регрессионные тесты). Паспорта банков в реестре из S5.
2. **Сверка:** правила практики и обучение на решениях специалиста; автоматическое подтверждение только при высокой уверенности (порог в настройках), остальное — подсказка.
3. **Согласия** — тот же `ConsentRecord` из S3: подключение банка и передача данных банку оформляются согласием; отзыв удаляет токены и прекращает синхронизацию в течение минуты.
4. **Страница и ссылка банка-партнёра** `/partner/<код>`: клиент, пришедший по ссылке, видит подключение счёта этого банка первым шагом; атрибуция хранится в `PartnerReferral`; другие банки доступны и не скрыты.
5. **Кабинет банка** (роль `bank_partner`): только агрегаты (пришло, активировано, подключено счетов, объём платежей через банк, воронка) и управление кодами; **ни одним маршрутом не возвращает данные фирм**; тест на все маршруты роли.
6. **Лиды по согласию:** клиент сам нажимает «Получить предложение банка»; банку уходит только выбранное клиентом, на срок; фиксируется в `ConsentRecord`.
7. **Песочница банка:** тестовые фирмы, счета и вебхуки, руководство.

### 7.3. Рынки (решение)
- **UA:** сначала monobank и ПриватБанк (уже есть); открытый банкинг НБУ (Положение № 80) подключаем **через авторизованного агрегатора**, собственную регистрацию провайдера не оформляем.
- **DE:** через лицензированного агрегатора (первый кандидат — finAPI; окончательный выбор после сравнения условий в S7); собственная регистрация в BaFin не оформляется; платёжные инициации — только через страницы банка/агрегатора.
- **UZ:** только импорт выписки файлом, пока Центробанк Узбекистана не опубликует правила для сторонних провайдеров (в источниках сроки расходятся: 2026 или поэтапно с 2027). Кнопок «подключить по API» нет.

### 7.4. Банки-кандидаты для пилота
Первыми предлагаем пилот **monobank** и **ПриватБанку** (интеграции уже есть), для Германии — банку, который поддерживается агрегатором и ориентирован на малый бизнес. Условия партнёрства (реферальное вознаграждение за активированного клиента, доля эквайринга, плата за брендирование) определяются в переговорах; договор без эксклюзивности и без доступа банка к данным клиентов — обязательное условие с нашей стороны.

## 8. Позиционирование и дифференциация

**Позиция (одно предложение):** Firmspace — учёт для малого бизнеса, где предприниматель и его бухгалтер работают в одном кабинете, ИИ помогает под их контролем, а правила рынка и банки подключены из коробки.

**Три обязательных демонстрации (должны работать в демо-кабинете и в ролике):**
1. «Оплата → за 30 секунд видна везде»: счёт, сделка, лента клиента, заказ, отчёты, открытые вкладки (уже работает).
2. «Закрыть месяц за час»: режим закрытия из S4 — неразнесённое, недостающие документы, расхождения, пакет бухгалтеру.
3. «ИИ с гарантиями»: Айрис и роботы ничего не меняют без подтверждения, не удаляют, пишут журнал и откатываются.

**Что мы не заявляем:** любые возможности в статусе `planned`; сравнительные цифры о конкурентах без источника; «юридическую безошибочность» документов.

**Чего не делаем:** не строим «ещё один универсальный учёт для всех»; фокус — рынки DE, UA, UZ и связка клиент–специалист–банк.

## 9. Исследование рынка
Материалы ведёт платформа: матрица конкурентов по рынкам (функции, цены, условия для специалистов и банков, регуляторика, источники) — `docs/research/competitors.csv`, `docs/RESEARCH.md`. **Интервью и «точка проверки спроса» из ТЗ убраны (решение владельца): S6 и S7 выполняются в полном объёме без условия входа.** Пустое поле цен и условий в матрице — «не найдено в открытых источниках», а не «бесплатно».

## 10. Требования качества ко всем спринтам
1. Ни один спринт не закрывается без: `tsc`, `next lint`, `next build`, `npm test` на PostgreSQL, проверки локалей, проверки в браузере по сценарию спринта.
2. Новые маршруты — в `moduleForPath` и `featureForApi`; тест на изоляцию «чужая фирма/практика/банк по id» на каждую новую сущность.
3. Схема базы только аддитивно; каждая миграция с отчётом «до/после» и планом отката; накатывается вручную по вашему слову.
4. Тексты — через `messages/{de,en,ua,uz}.json`; юридические тексты готовит юрист, не я.
5. Секреты шифруются, не попадают в журнал ИИ и ответы.
6. Правовые утверждения — только с источником и датой; без подтверждения — в интерфейсе предупреждение.
7. Документация обновляется в том же PR (`docs/SYNC.md`, `docs/UZBEKISTAN.md`, `docs/PROFESSIONALS.md`, `docs/BANK_PARTNERS.md`, `docs/ROBOT_OFFICE.md`).

## 12. Риски и что делаем
| Риск | Решение |
|---|---|
| Ошибка в правовых правилах UZ | бета-плашка, `verifiedBy`, разовая внешняя проверка, правила данными с датой |
| Нет доступов к ЭСФ/платежам | v1 готовит данные и файлы, v2 по договорам; кнопки только у `available` |
| Бухгалтеры отвергнут ИИ | роботы только под их контролем, правила практики, никаких «заменим бухгалтера» |
| Банки не заинтересуются | условие входа раздела 9; коннектор остаётся полезным и без партнёрств |
| Утечка профессиональной тайны | акцепт соглашений, запрет публичного ИИ по умолчанию, журнал доступа |
| Рост сложности | один спринт — одна главная сущность, тесты изоляции на каждую |
| Регрессия DE/UA при обобщении рынков | регрессионные тесты S1 до любых изменений |
