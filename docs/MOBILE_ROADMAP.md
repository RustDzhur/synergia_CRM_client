# Мобильные приложения: дорожная карта и статус

Архитектура и обязательные правила — `docs/MOBILE.md` (ссылки вида «MOBILE 6.3» — на его разделы). Здесь: порядок работ, решения, что нужно от владельца, статусы и журнал.

## Как работать по плану (протокол шага)

1. Прочитать `MOBILE.md` и этот файл целиком.
2. Взять первую задачу со статусом `[ ]` в самом раннем этапе. Исключения — только те, что помечены «параллельно» в разделе «Зависимости».
3. Ветка `feat/mobile-<этап>-<кратко>`. Работать только над этой задачей.
4. Выполнить критерий готовности задачи. Чего нельзя проверить здесь (реальное устройство, магазин) — не отмечать как проверенное.
5. Отметить статус и добавить строку в «Журнал выполнения» внизу: дата, задача, **что проверено и чем**, **что не проверено**.
6. Коммит локально, конкретными путями. Пуш и слияние в `main` — только по слову владельца «заливай» / «залей».
7. Ответ владельцу по-русски: что сделано, что проверено и что нет, что дальше.

Легенда: `[ ]` не начато · `[~]` в работе · `[x]` готово и проверено · `[!]` заблокировано (причина рядом).

## Журнал решений

Приняты по умолчанию, чтобы не стоять на месте. Меняются словом владельца; изменение записывается сюда с датой.

| № | Решение | Почему |
|---|---|---|
| D1 | Capacitor 8 + живой сайт (`server.url` = `https://www.firmspace.de`) | единственный вариант, где изменения сайта видны в приложении мгновенно (MOBILE 4) |
| D2 | Два бинарника: iOS универсальный, Android AAB. Отдельных «планшетных приложений» нет | экраны решает адаптивная вёрстка (MOBILE 2) |
| D3 | Название в магазинах «Firmspace AI», идентификатор `de.firmspace.crm` (предложение) | идентификатор после первой публикации изменить нельзя — подтвердить в U3 |
| D4 | Оболочка — отдельный репозиторий `~/Developer/firmspace-mobile`, локальный git | iCloud, `tsconfig` сайта, свои секреты (MOBILE 3) |
| D5 | Сессия устройства (deviceToken в Keychain/Keystore) + биометрия по желанию | сегодня токен на сутки без refresh (MOBILE 7) |
| D6 | Push через FCM на обеих платформах, ключ APNs — в Firebase | одна серверная отправка (MOBILE 8) |
| D7 | Тарифы и оплата скрыты в приложении; регистрация Free допустима | правила Apple 3.1.1 (MOBILE 12.3) |
| D8 | OAuth через системный браузер, возврат по `firmspace://` | Google запрещает OAuth в WebView (MOBILE 9.3) |
| D9 | Телефоны — только портрет; планшеты и складные — любая ориентация | проще макет телефона; Google/Apple ждут ориентаций на планшетах |
| D10 | Телефон: нижняя панель вкладок + «Ещё» из `menuItems` — для всех телефонов. Планшет: свёрнутый сайдбар и две панели на `tab` | MOBILE 11.2 |
| D11 | Новый брейкпоинт `tab: 1024px`, существующие не меняются | iPad в ландшафте попадает между `mp` 900 и `lg` 1440 |
| D12 | Push о дедлайнах — после первого релиза | нужен серверный планировщик чаще суток (MOBILE 8) |
| D13 | Удаление аккаунта: владелец фирмы с другими участниками сначала передаёт владение (иначе удаление блокируется с пояснением); единственный участник — фирма и данные удаляются после подтверждения паролем; подписка Stripe отменяется | требование 5.1.1(v) без потери чужих данных |
| D14 | Первый релиз — после адаптации P0 и P1; P2 добирается обновлениями сайта уже после релиза | обновления сайта не требуют магазина (MOBILE 1) |
| D15 | Локальная база офлайн-режима — нативная SQLite (SQLCipher, ключ в Keychain/Keystore) и для кеша, и для очереди правок; IndexedDB для данных CRM не используем; в браузере офлайн-слоя нет | выбор владельца 2026-09-30: очередь неотправленных правок нигде больше не хранится, а хранилище WebView система может очистить (MOBILE 18.2) |
| D16 | Интерфейс без сети: по умолчанию service worker на неизменяемые ассеты; запасной вариант — офлайн-мини-приложение в оболочке, только по слову владельца | решается спайком M7.0 (MOBILE 18.8) |
| D17 | Офлайн-ядро: контакты, компании, сделки, задачи, календарь, заметки, фото; заказы — чтение; деньги, чеки, доставка, сообщения — только онлайн. Конфликт по одному полю решает человек («Проверить») | по умолчанию (MOBILE 18.1, 18.6) |

## Зависимости и параллельность

* Этап 1 идёт первым, но M1.6–M1.13 не блокируют начало этапа 3.
* Этап 3 (оболочка) можно начинать, когда готовы M1.1–M1.5 (сайт знает режим приложения и отдаёт конфиг). Этапа 2 для этого ждать не нужно.
* Этап 4 требует этапа 3, M1.5 и M1.7. M4.4 требует U1 и U2.
* Этап 2 (адаптация) идёт параллельно этапам 3–4; **отправка в магазины требует M2.1–M2.9**.
* Этап 7 (офлайн) идёт после релиза (этап 6) и требует M4.1 (сессии на 90 дней), M4.3 (push) и каркаса оболочки этапа 3.
* **Таймер Google (14 дней)** запускаем, как только есть Android-сборка с входом и страницами P0 (после M2.3–M2.7, M4.1): не ждём M5.4.
