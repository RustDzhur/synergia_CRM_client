# Приём оплаты в Узбекистане: Payme и Click (S8)

Принцип (docs/TZ_MASTER.md §6.4): договор с Payme или Click заключает сама фирма и получает свои ключи; платформа даёт готовый модуль по официальной документации, защищённую форму ключей, адрес для кабинета провайдера и ссылку на оплату в счёте. Деньги идут напрямую фирме.

Статус обоих модулей — `beta`: написаны по документации (проверена 2026-10-05) и проверены тестами протокола (`tests/uzPay.test.ts`); на живых ключах провайдеров пока не проверялись. Снятие `beta` — после прохождения песочницы Payme и тестовых сценариев Click на ключах первой фирмы (кнопка статуса в админке паспортов).

Только сумы (UZS): счёт в другой валюте ссылку не получает.

## Payme Business — Merchant API
Источники: developer.help.paycom.uz (Протокол Merchant API, Методы, Инициализация платежей, Песочница).

1. Фирма заключает договор, создаёт в Payme Business веб-кассу с полем счёта `order_id` (одноразовое).
2. Settings → Integration → Payme: Merchant ID кассы, ключ кассы, тестовый ключ (TEST_KEY); флажок «режим песочницы» включён по умолчанию.
3. После подключения окно показывает **Endpoint URL** (`/api/webhooks/payme/<маркер фирмы>`): его вписывают в настройки кассы.
4. Два сценария песочницы test.paycom.uz (создать/отменить; создать/выполнить/отменить) проходят с тестовым ключом. Затем режим песочницы снимают — ссылки ведут на checkout.paycom.uz.

Реализовано: авторизация `Basic base64("Paycom:<ключ>")` (код -32504), CheckPerformTransaction, CreateTransaction, PerformTransaction, CancelTransaction, CheckTransaction, GetStatement, SetFiscalData (принимается без изменений); состояния 1/2/-1/-2, причины как прислал Payme, таймаут созданной транзакции 12 часов (причина 4), идемпотентные повторы, ошибки -31001, -31003, -31007, -31008, -31050 (с полем `data`), локализованные сообщения ru/uz/en. Оплата засчитывается через `registerPayment`, возврат после выполнения — через `revertPayment` (в закрытом периоде отмена отклоняется кодом -31007).
Ссылка на оплату: `https://checkout.paycom.uz/` + base64(`m=…;ac.order_id=<номер счёта>;a=<тийины>;l=<язык>;c=<возврат>;cr=860`).

Не реализовано: передача фискальных данных в `detail` (ИКПУ и коды упаковки товаров появятся в карточках товаров), цепочечные платежи (`receivers`).

## Click — SHOP API
Источники: docs.click.uz (Shop API: запросы, ошибки; Платёжная ссылка).

1. Договор с Click; в кабинете Click Merchant — Merchant ID, Service ID, Secret key.
2. Settings → Integration → Click: эти значения (Merchant user ID — по желанию).
3. Окно показывает адрес `/api/webhooks/click/<маркер фирмы>`: его указывают в кабинете и как Prepare URL, и как Complete URL (действие различается полем `action`).

Реализовано: проверка подписи MD5 (для Complete — с `merchant_prepare_id`), проверка `service_id`, Prepare (резерв и проверка суммы с допуском 0,01), Complete (зачёт оплаты, повторы возвращают -4, отмена со стороны Click возвращает -9), коды -1…-9. Ссылка: `https://my.click.uz/services/pay?service_id&merchant_id&amount=N.NN&transaction_param=<номер счёта>&return_url`.

Не реализовано: Merchant API Click (возврат платежа, статус платежа), Split Shop, Advanced Shop, Click Pass.

## Хранение и проверка
Таблица `UzPayTx` (провайдер, внешний id, счёт, сумма, состояние) — для идемпотентности и сверки. Кнопка «Проверить подключение» показывает, дошёл ли хотя бы один запрос провайдера. Номер счёта ищется только среди счетов этой фирмы; транзакции чужой фирмы не видны (тесты).
